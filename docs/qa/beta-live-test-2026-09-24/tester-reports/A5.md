## 4. Findings

### Medium — `POST /api/inventory/drop` ignores the `quantity` field; always drops the entire stack

- **Location**: `src/api/routes/inventory.py`, `drop_item()` (~line 168-220)
- **Steps to reproduce**:
  1. Login, own a stack of 5 Restoratives (`b973e3764a7b478db8ac3faf653d01f5`).
  2. `POST /api/inventory/drop {"item_id": "<restorative>", "quantity": 1}`
  3. `GET /api/inventory` — the entire 5-item stack is gone, not just 1.
- **Expected**: dropping quantity 1 of a 5-stack leaves 4 in inventory and puts a 1-count item on the floor tile.
- **Actual**: the whole stack (5) is removed from inventory in one call. `result = game_service.drop_item(player, item_to_drop)` is called with no quantity argument at all — the route reads `quantity` from the request body in `drop_item()`'s docstring-adjacent code but never actually uses the variable (there isn't even a local `quantity = data.get(...)` line, unlike `/shop/buy` and `/shop/sell` which do this correctly).
- **Evidence**: `RUNS/A5_api.jsonl` line ~393 `"req": {"item_id": "b973e3764a7b478db8ac3faf653d01f5", "quantity": 1}` → `"message": "Item dropped"`; subsequent `/api/inventory` call shows no Restorative entry at all (confirmed via `KeyError` when indexing by type in a follow-up script, then confirmed directly with `next((i for i in inv if i["type"]=="Restorative"), None)` → `None`).
- **Confidence**: reproduced once, root cause confirmed by reading the route source (no quantity handling exists in the function body at all — this isn't a rare edge case, it's unconditional).
- **File**: `src/api/routes/inventory.py:168-220` (`drop_item`)

### Low — inconsistent HTTP status for "target not found" on `/api/world/interact`

- **Location**: `src/api/routes/world.py` (interact handler)
- **Steps to reproduce**: `POST /api/world/interact {"target_id": "<id belonging to a different tile>", "action": "enter"}`
- **Expected**: consistent with other reject paths in the same route family (`/api/world/move` → 400 "Cannot go X from here"; `/api/world/events/input` on unknown event → 400 "Event ... not found") — a not-found target should be 400 or 404.
- **Actual**: `200 {"success": false, "message": "Target not found."}` — a 2xx status carrying a failure payload.
- **Confidence**: reproduced twice (once against a cross-tile object id, once against a raw shop-stock id passed to `/api/world/interact`). Low severity since no state corruption results and `success:false` is present, but it breaks the "check status code" habit an API client would reasonably rely on.

### Low — Vacated Dwelling side map plays Mineral Pools BGM

- **Location**: `src/resources/maps/grondia-vacated-dwelling.json` (both "Main Chamber" (2,2) and "Inner Room" (2,1))
- **Actual**: `/api/world` room payload reports `"bgm": "mineral_pools"` for both rooms of the Vacated Dwelling, a residential side-map with no connection to the Mineral Pools story area.
- **Expected**: an ambient/interior track appropriate to a quiet abandoned home, or inherited `"grondia"` bgm.
- **Confidence**: seen directly in both rooms of the map; likely a copy-paste default left over from another map's template rather than deliberate. Cosmetic only — flagging since it's an easy one-line JSON fix.

### Observation — Ch02GuideToCitadel blocks movement without saying so

- While the Ch02GuideToCitadel event is pending (unanswered), `POST /api/world/move` for a *valid* exit direction returns `200 success:true` with the *same* `new_position` as before the call — i.e. it silently no-ops instead of returning a "movement blocked, resolve the pending event first" error. Contrast with the deliberate no-exit-direction case, which correctly returns `400 "Cannot go X from here"`. A client naively checking only `success` would think the move worked. Not confirmed as a general rule (only observed for this one event, encountered incidentally while the automated crawler revisited (7,5) mid-event); flagging as an observation rather than a hard finding since it may be scoped narrowly to blocking dialogue events by design.
- **Confidence**: seen twice for the same event (`RUNS/A5_api.jsonl` lines ~62, ~251), same event_id both times, both times `new_position` unchanged from the pre-call position.

## 6. Non-bug observations

- Starting gold on `api0924` was 315, not the 300 stated in the primer's stack table — trivial drift, not tested further.
- `/api/inventory/compare` requires an explicit `current_index` query param to compare against the currently-equipped item in that slot; it does not auto-infer "whatever is equipped in this item's slot." Calling it with only `candidate_index` correctly reports `"reason": "No item currently equipped"` even when something *is* equipped, because nothing was asked to compare against. This is documented behavior (the docstring calls `current_index` optional), not a bug — but it's an easy trap for a QA tester or a frontend integrator to misread as a state bug. Worth a one-line docstring clarification.
- The item picked up from Jambo's floor drop (after the merchandise-rule test) came back into inventory with `"is_merchandise": true` even after being carried and re-dropped once, while normally-owned items show `false` — cosmetic metadata artifact, did not cause any gameplay-visible issue (it was correctly caught and reset ("Jean sets Restorative down; unpaid goods don't leave the shop.") on the very next passage crossing, which is the merchandise-rule assignment item — **confirmed PASS**, the API does tell the player, with a clear in-fiction message).
- All 38 Grondia tiles' descriptions matched `grondia.json` byte-for-byte on the first 80+ characters checked; exits matched the JSON's `exits` list exactly on every tile; no orphaned/undocumented objects were found.
