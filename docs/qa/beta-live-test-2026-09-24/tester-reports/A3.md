## 4. Findings

### Finding #1 — Seed config `config_qa_leg_0924.ini` sets `king_slime_defeated` without granting the `MineralFragment`, permanently blocking `AfterKingSlimeReturn`

- **Severity**: Critical (blocks the entire assigned route for this tester; not a live-game bug but a QA-harness defect that made the assignment unexecutable past step 1)
- **Location**: `config_qa_leg_0924.ini` (seed config), consumed by `src/config_manager.py`, affecting `src/story/ch02.py`
- **Steps to reproduce** (from login):
  1. `A3 login 5003` — starts at Grondia (7,9), `king_slime_defeated` and `lurker_defeated` already set per `starting_story_flags`.
  2. `GET /api/inventory` — no `MineralFragment` present (items: TatteredCloth, ClothHood, JeanWeddingBand, 2×Restorative, Antidote, Shortsword, RustedIronMace, LeatherArmor, LeatherCap, LeatherGloves, LeatherBoots, Gold).
  3. Walk to Grondia (10,5) Citadel (path: NE, NE, NE, NE, E, E, E, E from (7,9), then W×5).
  4. `POST /api/world/events {}` at (10,5) — returns `200` with no `message` and zero pending events afterward (`GET /api/world/events/pending` → `{"events": []}`).
- **Expected**: `AfterKingSlimeReturn` should fire on this Citadel visit (that's the explicit design intent per the config's own header comment: *"...so the Citadel aftermath (AfterKingSlimeReturn at (10,5))... are all live"*), presenting Votha Krr's greeting and the fragment hand-over choice.
- **Actual**: Nothing fires. No error, no crash — the event simply never becomes eligible.
- **Root cause**: `AfterKingSlimeReturn.check_conditions()` (`src/story/ch02.py:1521`) requires `self._has_fragment()` — the player must be carrying a `MineralFragment` item, not just have the `king_slime_defeated` story gate. In normal play, the fragment is granted programmatically inside `AfterDefeatingKingSlime.process()` (`src/story/ch02.py:884-891`, comment: *"Grant the MineralFragment straight to Jean's inventory... Spawning it as a floor item relied on the player picking it up..."*) at the same time that event sets the `king_slime_defeated` gate (`ch02.py:899`). The QA seed config sets `starting_story_flags = king_slime_defeated, lurker_defeated` directly via `src.config_manager` (writes straight into `universe.story`, `config_manager.py:328-335`), which sets the gate but never runs `AfterDefeatingKingSlime.process()`, so the fragment grant is skipped entirely. There is also no floor copy of the fragment anywhere (by design, per the same comment) and no `/api/debug/*` route that can add an inventory item (`src/api/routes/debug.py` only exposes player stat/level/attribute/heat/restore/skill and arena-roster ops — no item grant). Net effect: this session can never legitimately acquire the `MineralFragment`, so `AfterKingSlimeReturn` can never fire, `votha_krr_response_given` can never be set, and the Eastern Gate (`locked_until_flag: "votha_krr_response_given"`) can never open in this session.
- **Confidence**: High / reproduced consistently — read from source (three independent call sites agree: the event's own condition check, the granting event's comment explaining why it's granted programmatically rather than left on the floor, and the config file's own starting_items list, which lists `Restorative, Restorative, Antidote` and omits `MineralFragment`), and confirmed empirically via `/api/inventory` and two separate `/api/world/events` triggers at the Citadel tile.
- **Suggested fix**: add `MineralFragment` to `starting_items` in `config_qa_leg_0924.ini` (it's a plain `Special` item class per `src/items.py:3734`, so it should parse the same as the other starting items). This is a config-only fix, not an engine change — I did not attempt it since editing ROOT is out of scope for this tester.
- I did **not** use `/api/debug/*` to get past this blocker: no such endpoint exists (debug routes are stat/level/attribute/heat/restore/skill/arena-only), so there was no test-only workaround available.
