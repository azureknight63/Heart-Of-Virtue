## 4. Findings

### Finding 1 — Scene 6 (MaraObservationEvent) fires immediately after Scene 5d, not on a literal "re-entry" (Low, informational)

- **Severity**: Low (design/documentation mismatch, not a functional bug)
- **Location**: `eastern-descent-nomad-camp` (1,2) Rivers Edge
- **Steps to reproduce**: Visit Devet (5b) and Liss (5c) *before* visiting Mara (5d) for the first time, then approach Mara.
- **Expected** (per assignment route, mirroring the docstring "Fires once on Jean's re-entry to RiversEdge (1,2)"): Scene 6 requires leaving the tile and coming back after visiting the Tradepost.
- **Actual**: `MaraObservationEvent.check_conditions` (`src/story/ch03.py:1118`) only checks that `MaraFirstContactEvent`, `DevetIntroEvent`, and `LissObservingEvent` gates are all set (`PREREQUISITE_BEATS` at `ch03.py:1109`) — it does **not** require `IronAndOathIntroEvent`/`AnvilIntroEvent`. Since I did Devet and Liss before Mara, all three prerequisite gates were already true the instant Scene 5d (MaraFirstContact) finished, so Scene 6 chained immediately in the same dialog session (shown as log stage `[2]` right after `[1]`), without ever actually leaving the tile.
- **Confidence**: Reproduced once, but the causal chain is clear from source — this is deterministic given visit order (Devet+Liss before Mara), not a race.
- **Suspected cause**: Not a bug — `PREREQUISITE_BEATS` correctly excludes the Tradepost beats. The assignment's expected sequencing (5e before Scene 6) assumes a route where prerequisites aren't all satisfied until after the Tradepost, which doesn't hold for the Devet→Liss→Mara visit order. I did verify the event does **not** double-fire on a genuine re-entry afterward (see route checklist), so the gate/repeat logic itself is correct.
- **Recommendation**: No code change needed. Worth updating the QA route notes so future testers aren't confused when Scene 6 fires "early."

### Finding 2 — Two consecutive LLM replies degrade to scripted fallback, then the conversation silently self-exhausts with no visible closing message (High)

- **Severity**: High (breaks the core deliverable of this tester's assignment — live NPC conversation — and burns shared LLM quota for no value)
- **Location**: `grondia-jambos_shop` (2,2) with Jambo; `eastern-descent-nomad-camp` (1,2) with Mara
- **Steps to reproduce**:
  1. Talk to Jambo. First reply is real (LLM-generated). Second reply (after clicking a reply option) returns banner *"Connection unavailable — this reply is scripted, not generated."* with fallback text *"Jambo falls quiet a moment, considering."* A third reply attempt returns the same banner again, and the dialog silently reverts to the buy/sell/trade/talk target menu with no "conversation ended" screen.
  2. Same pattern independently with Mara: 1st exchange real, 2nd exchange degraded, retried once (per primer's rule), degraded again, conversation silently ended.
- **Expected**: Either the LLM call succeeds, or if it fails, the game degrades gracefully per `.claude/rules/combat-engine.md` ("NPC chat / LLM code must degrade gracefully... never surface a stack trace"). A single scripted-fallback line met that bar, but the conversation then vanished without any visible transition.
- **Actual**: Confirmed via direct API check on Mara: `POST /api/npc/chat/open {"npc_id":"Mara"}` returned `{"conversation_ended": true, "llm_available": false, "loquacity_current": 0, "loquacity_max": 12, "npc_opening": "", "npc_flavor": "Mara turns back to what she was doing. The conversation is over."}` — an exact match to Mara's authored `closing_lines_when_exhausted[0]` in `ai/npc/human/mara.json`. So the closing behavior *is* using authored content correctly, but the UI never displayed a distinct "conversation has ended" screen — it just silently swapped the chat dialog back to the object-interact menu between one poll and the next, which reads as the chat vanishing/glitching rather than concluding.
- **Evidence**: Screenshots `T5_005_jambo_degraded_fallback.png`, `T5_006_jambo_convo_autoclosed.png`, `T5_022_mara_degraded_exchange2.png`, `T5_023_mara_convo_autoclosed.png`. No console/network errors were logged for these transitions (`allerrors` returned clean each time) — the degradation is silent even to devtools.
- **Confidence**: Reproduced twice (Jambo and Mara, independently, same failure shape) — strong evidence this is systemic to the LLM backend connectivity during this test window, not per-NPC.
- **Suspected cause**: Not source-verified within budget, but `llm_available: false` plus `loquacity_current: 0/12` after only 3 total exchanged messages with Mara suggests either (a) failed calls are consuming loquacity at a much higher rate than successful ones, compounding a transient provider outage into a hard stop, or (b) the provider was genuinely down/rate-limited for a stretch of this run and loquacity depletion is coincidental. Recommend checking backend logs for `provider=` / `result_chars=` around 14:36–14:45 and 15:07 (`.claude/rules/llm-prompts.md`'s guidance on checking *who answered*) to distinguish a dead-provider incident from a design gap in the conversation-ended UI transition.
- **Note for the shared LLM quota**: both retries were used exactly once per the primer's cap rule before moving on; no extra requests were burned chasing this.

### Finding 3 — Jambo's (unauthored, generated-personality) opening line gives hyper-specific river-crossing navigation advice that is thematically Mara's, not his (Low)

- **Severity**: Low (voice/lore consistency, not a functional bug — Jambo has no authored persona by design)
- **Location**: `grondia-jambos_shop` (2,2), Jambo's first LLM reply
- **Steps to reproduce**: Talk to Jambo in his tent (Grondia), before Jean has ever traveled to the Eastern Descent or nomad camp.
- **Expected**: Per `src/npc/_merchants.py:208-231`, Jambo is "a nomad healer and potion merchant" with no authored persona; his generated personality should stay in that generic apothecary/merchant lane.
- **Actual**: Jambo's opening line was: *"Jambo taps the bank with a staff and nods toward the reeds. The river's running high, and the west-bank ford is no place for a stubborn mule. Watch the reeds—the shallow line runs between the third and fourth stones."* This is extremely specific river-crossing/ford navigation advice — content that matches Mara's authored `knowledge_scope` almost exactly ("river crossings and current behavior"). Jean has not yet met Mara, seen the river, or heard of any ford at this point in the story (he's still in Grondia, an inland city).
- **Confidence**: Seen once (single sample from the generated fallback personality); the header/portrait correctly said "Jambo" throughout (#599 is genuinely fixed at the UI level), so this is a content-generation lore leak, not a UI mislabel regression.
- **Suspected cause**: Jambo's "generated/story" personality (`_ensure_personality`, referenced in the class docstring) appears to produce travel-advice flavor text without being scoped away from river/crossing topics that belong to a not-yet-met, geographically-distant NPC. Not verified against the actual prompt-construction code within budget.

## 7. Non-bug observations

- Combat pacing at level 3 is fatigue-gated, not HP-gated (see Combat Log) — feels a bit grindy (multiple forced Rest turns per fight) but never dangerous; worth a design look for #581 but not filing as a bug.
- The `📜 LOG (n)` button and its `↩ Back` control worked well for retrieving exact prose after a multi-stage scene — useful for QA, and presumably for players who want to re-read.
- Loot collection UI (Take All / Leave All / Collect Selected) was smooth and fast across both post-combat loot screens.
- The room re-entry "story"-styled description dialog (distinct from scripted STORY events — just the room's flavor text re-shown in a dialog with a CLOSE button) appeared unexpectedly a few times when re-entering a previously visited tile (e.g., back at Ecumerium (12,4) after leaving Jambo's tent) and briefly blocked movement-button clicks until dismissed. Not filed as a bug (didn't lose the game state, just needed one extra CLOSE click), but flagging as minor UX friction worth a look.
