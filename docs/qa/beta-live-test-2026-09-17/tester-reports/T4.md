## 7. Findings

### Finding 1 — Low: battlefield drag-to-pan only works in "Follow" view mode, not "Fit Fight"
- Severity: Low (UX clarity, not a functional bug)
- Location: combat UI, Battlefield Map panel, any fight
- Steps: enter any fight (tested at (1,2) vs Rock Rumbler Nihmejej) → note "Fit Fight" is the default active view mode → attempt a mouse drag (both native Playwright mouse events and synthetic PointerEvents) on the battlefield canvas → no visible pan (confirmed via DOM transform matrix staying `matrix(1,0,0,1,0,0)`) → switch to "Follow" mode → same drag → view pans correctly (nodes shift position, a map-boundary dashed line becomes visible)
- Expected/Actual: #592 says "drag-to-pan reveals new map area." This works, but only after switching off the default "Fit Fight" mode. A player who never touches the Follow/Fit Fight toggle may conclude drag-pan is broken.
- Evidence: screenshots `T4_006` through `T4_015`; DOM inspection via `page.evaluate` confirmed zero transform change in Fit Fight mode across 3 drag attempts (native mouse + 2 synthetic pointer-event variants)
- Confidence: reproduced twice (Fit Fight failing to pan; Follow succeeding)
- Suspected cause: "Fit Fight" mode likely re-centers/re-fits the view on every combat-state poll, which would overwrite any manual pan offset each tick — plausibly intentional (the mode's whole purpose is auto-fit), but worth a one-line disabled-state or tooltip so a tester/player doesn't mistake it for a broken drag handle.

### Finding 2 — Low (non-bug, testing-methodology note worth flagging): the "Wait" move opens an unlabeled-in-status "Enter beats" dialog; if unanswered, combat appears server-side frozen to anyone polling `/api/combat/status` alone
- Severity: Low / process note, not a product bug
- Location: combat UI, DEFENSIVE/MISC move panel, any fight (reproduced at (5,1) North Face Trail vs Rock Rumbler Otenneer)
- Steps: during a fight, open MISC → click "Wait" → a "🔢 ENTER VALUE — How many beats do you want to wait?" modal opens (range 3-10, default 5) → if you don't click CONFIRM and instead only poll `get('/api/combat/status')`, `beat`/`round` and every combatant's `move_in_process.beats_left` stay byte-for-byte identical indefinitely (confirmed frozen for 45+ seconds and across a full page reload)
- Expected/Actual: I initially mis-read this as a Critical combat soft-lock (beat counter genuinely not advancing, identical state across reload). It resolved instantly once I clicked CONFIRM on the modal — beat jumped 17→22, HP updated. So this is not a lock; it's correct behavior (an unanswered input dialog blocks resolution) — but the API status payload gives no hint that a client-side modal is pending (no `input_type` flag distinguishing "choose a beats value" from "choose a move"), which makes it easy to misdiagnose as a stall when driving/monitoring via the REST layer instead of the DOM.
- Evidence: repeated identical `/api/combat/status` polls at 14:36:37→14:37:0x (Jean's Attack `beats_left: 4`, Gorran `beats_left: 0`, Rock Rumbler `beats_left: 1`, all static); reload at that point re-displayed the same "ENTER VALUE" dialog (proving it was a genuine pending client input, not a rendering glitch); CONFIRM immediately unstuck it
- Confidence: reproduced once, root-caused conclusively via the reload test
- Suggested improvement (not a required fix): surface `input_type: "beats_value"` or similar in `/api/combat/status` so anything driving combat over the API (bots, other testers, future automation) can distinguish "no dialog, just still resolving" from "blocked on a modal I can't see."

### Finding 3 — Low: Gorran transiently absent from the room's NPC list immediately after the RoadEast turnback event
- Severity: Low
- Location: eastern-descent (5,4) Adders Shelf, immediately after the (6,4) RoadEast turnback
- Steps: from (5,4), defeat the Scarp Adder → collect loot → move east into (6,4) → EasternRoadTurnbackEvent fires and returns Jean to (5,4) → `where()` on landing shows `npcs: []` (Gorran missing) despite `/api/status` still listing him in `party_members` with full HP
- Expected/Actual: Expected Gorran to remain listed as present on the tile (as he was on every other tile, including the very next tile (3,5) where he reappears normally). Actual: one-tile gap in the room NPC listing right after the turnback teleport.
- Evidence: `where()` output at (5,4) post-turnback: `'npcs': []`; `/api/status` same moment: `party_members: [{'name': 'Gorran', 'hp': 228, ...}]`
- Confidence: seen once, did not attempt to reproduce a second time (budget)
- Suspected cause: the turnback event likely repositions the player via a code path that doesn't re-sync ally-render state for that single frame/response (similar in shape to the tile/room param bug previously fixed for `trigger_tile_events`/`trigger_combat_events` — see MEMORY.md fixed-bugs note about `event.tile = player.current_room`).
