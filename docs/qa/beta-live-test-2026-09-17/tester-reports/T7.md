## 4. Findings

### Finding #1 — Crate `take`/`take_all` items vanish from inventory and reappear on an unrelated tile's floor (supersedes #600's documented symptom)

- **Severity: Critical** (silent item loss / item misplacement, no error surfaced to the player)
- **Location**: `eastern-descent-jambos-tent` (3,2) Jambo's Tent Storage — the Crate; items resurface at (2,2) Jambo's Tent Entrance
- **Steps to reproduce** (from session start, after reaching Jambo's Tent Storage):
  1. INTERACT → Crate → single `TAKE` on "Dried Crystal Sap ×2". UI reports "Jean takes Dried Crystal Sap x2."
  2. Click `TAKE ALL` on the remaining stacks (Iron Ration ×2, Mineral Solvent, Slime Flask, Restorative, Draught ×3, Respite, Wooden Arrow). UI reports success and "The container is empty."
  3. Leave via Tent Flap keyword, walk back through (3,2)→(2,2).
  4. Check inventory via `GET /api/inventory`: none of the 8 taken item types are present (14 items total — starting kit + combat drops only).
  5. Check the room at (2,2) via `GET /api/world`: all 8 taken item names appear there as fresh floor items with new unique ids (e.g. `Dried Crystal Sap x2` / id `57e657ea...`), alongside 20 unrelated `merchandise: true` floor items (Baselard, Studded Boots, Hammer, Shortsword, Longsword, Fabricarium Compact Seal, Dissenting Record — The First Dormancy, Merchant's Journal Fragment ×2, etc.) that were **not present** at (2,2) on first visit (confirmed via `where()` showing `items: []` on the very first pass through that tile).
- **Expected**: Both single Take and Take All add items to `player.inventory`, matching the "Jean takes X" narration.
- **Actual**: Items are removed from the crate, the UI reports success, but the items never reach player inventory — they surface as floor items on a different tile (2,2), not even the tile the crate is on (3,2).
- **Evidence**: `logs/qa/runs-0917/shots/T7_004_t7_600_items_misplaced_2_2.png`; API responses captured live via `GET /api/inventory` (14 items, no crate items) and `GET /api/world` (28 room items at (2,2) including exact crate item names/quantities).
- **Confidence**: reproduced once with clear before/after API evidence (tile started empty, ended with the exact taken items). Did not have budget to repeat on a second run.
- **Suspected cause**: `Container.take_all()` (`src/objects.py:605`) and the single-take branch in `game_service._dispatch_interaction` (`src/api/services/game_service.py:2547-2559`) both call `transfer_item(source, player, item, qty)` from `src/inventory_utils.py`, which appends to `target.inventory` — structurally this should be correct since `player` is passed through directly from the route. The mismatch between the crate's tile (3,2) and the tile where items actually appear (2,2) suggests a stale `player.current_room`/tile reference somewhere in the response-building or persistence path (`persist_tile_state`, `apply_tile_modifications`) is writing the transferred items back into whichever tile's floor-item list was cached from an earlier request — parallel to the documented `player.current_room` staleness pattern already called out in `.claude/rules/api-layer.md` for `trigger_tile_events`. I did not have budget to trace further into `persist_tile_state`/`apply_tile_modifications`.
- Additionally: the pre-existing 20-item `merchandise: true` pile at (2,2) (Baselard, Fabricarium Compact Seal, Dissenting Record — The First Dormancy, etc.) appears to be a QA-config seed (map JSON has **zero** authored items at (2,2): `eastern-descent-jambos-tent.json`'s `(2,2)` entry has `items: []`), and some of the item flavor text (referencing "the voided mold downstairs" and "component locker") is clearly written for a different game area (a Fabricarium/foundry storyline), not a nomad-camp merchant tent. Flagging for narrative-review awareness; **not** filing as a game bug since it is very likely QA scaffold data from `config_qa_camp.ini`, not shipped beta content.

### Finding #2 — Reload mid-scene resurfaces a stale, already-resolved Victory/Loot dialog instead of resuming the current scene

- **Severity: High** (confusing UX, temporarily blocks the correct current story scene; does not corrupt game state)
- **Location**: nomad-camp (3,2) Fire Ring, during DevetIntroEvent (stage 2 of a multi-stage dialogue)
- **Steps to reproduce**:
  1. Trigger DevetIntroEvent, advance to its 2nd stage (text still showing conversation, not yet closed).
  2. `page.reload()`.
  3. Observe: page briefly shows a stale "Heart of Virtue - Combat" header with the "Victory! Gained exp: Basic: 20, Bludgeon: 28" summary from the **Talus Hound fight at Hounds Warren (3,4) on eastern-descent**, several tiles and multiple actions ago — a fight already fully resolved and looted earlier in the session.
  4. After ~4s, this resolves into the full "⚔ VICTORY — COLLECT YOUR LOOT" dialog offering "Gold ×31" to collect — the exact loot from that already-collected fight.
  5. Clicking "COLLECT SELECTED ITEMS" is a no-op (gold stays at 346 before and after — no duplication), and the client then correctly snaps to the true current state (Fire Ring, DevetIntroEvent already resolved — confirmed complete via the Story Log, which contains the full Devet conversation text).
- **Expected**: A reload mid-scene should either resume the current scene or drop cleanly into exploration reflecting the actual current engine state — not replay a UI artifact from several actions in the past.
- **Actual**: The frontend briefly replays a stale, already-resolved combat/victory screen before self-correcting. No data loss occurred (gold/story flags ended up correct), but the player is blocked from interacting with the actual game for several seconds and sees confusing, contradictory information.
- **Evidence**: `logs/qa/runs-0917/shots/T7_005_t7_stale_victory_after_reload.png`; gold cross-checked via `GET /api/status` immediately before (346) and after (346) the phantom collect.
- **Confidence**: reproduced once (this specific mid-scene reload was only attempted once per the assignment). The earlier reload test (#570, right after Rock Rumbler) looked superficially similar but that time the Victory state WAS still current — this second reload is what exposed the staleness, since much more had happened since the cached state was captured.
- **Suspected cause**: likely a client-side cache (localStorage/sessionStorage or a React state rehydration path) restoring the last-seen "combat ended" UI snapshot on reload before the fresh `/api/world` or `/api/combat/status` poll overwrites it, rather than gating the initial render on a fresh state fetch.

### Finding #5 — Traveler's Logbook dialog controls transiently disabled during the `read` request

- **Severity: Low** (no functional impact observed)
- **Location**: nomad-camp (2,3), Traveler's Logbook
- **Detail**: Immediately after clicking `read`, one `aria()` snapshot showed all dialog controls (← Back, read, examine, use, even ✕) disabled with no close control visible; a follow-up snapshot ~1s later showed them all re-enabled with the entry text and pager (← PREV/CLOSE/NEXT →) rendered normally. - **Confidence**: seen once, likely a network-latency artifact, not a genuine soft-lock.
