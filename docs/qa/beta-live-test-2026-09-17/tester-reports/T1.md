## 4. Findings

### Finding 1 — Reload after combat (even well after) re-renders a stale Combat/Victory screen with a React infinite-update warning
- **Severity:** High
- **Location:** `grondelith-mineral-pools` (2,3) Deep West — but the state is client-cached, so it reproduces regardless of tile
- **Steps to reproduce:**
  1. Defeat any enemy pack in combat, collect loot, return to exploration
  2. Walk 2+ tiles away from the fight location (confirms this isn't literally "reload immediately")
  3. `page.reload()`
- **Expected:** Client re-syncs to the engine's exploration state (per #570's fix)
- **Actual:** The page re-renders `Heart of Virtue - Combat` with the old Victory dialog's stats, and the console logs:
  ```
  Warning: Maximum update depth exceeded. This can happen when a component calls setState
  inside useEffect... at CombatLog (.../src/components/CombatLog.jsx:45:37)
  ```
  fired twice. `where()` (engine truth) correctly reports exploration state (npcs: [Gorran], no combat) the entire time — this is purely a frontend desync. Clicking the replayed dialog's Close button (twice — once for Victory, once again for the collect-loot dialog that reopens under it) does recover to normal exploration.
- **Evidence:** `T1_017_reload_bug_stuck_on_combat_screen.png`; console error text quoted above; corroborated independently by tester T3 (`T3_011_postfight_reload_stuck.png`) and T7 (`T7_005_t7_stale_victory_after_reload.png`) in the same run
- **Confidence:** Reproduced twice in this session's own combat sequence (implicitly — the same client-side combat-log persistence caused the reopened loot dialog on the *next* victory too), plus 2 other testers hit the same symptom independently
- **Suspected cause:** `frontend/src/components/CombatLog.jsx:45` — a `setState` in a `useEffect` without a stable dependency array, likely triggered when the component mounts against combat state that's already terminal (post-Victory) rather than active. The persisted/rehydrated combat state on reload appears to restore the whole in-combat UI tree (including the Victory dialog) instead of checking that the engine is no longer in combat before deciding what to render.

### Finding 2 — Loot dialog can silently leave items uncollected if "Take All" is clicked without following through
- **Severity:** Low
- **Location:** `grondelith-mineral-pools` (2,5) after the single-slime fight
- **Steps to reproduce:**
  1. Win a fight, open the Victory dialog, click "COLLECT LOOT →"
  2. Click "Take All" (selects items) but the subsequent script/user does not also click "COLLECT SELECTED ITEMS (n of n) →"
  3. Close the dialog via `✕` (which appears to work) and move to another tile
  4. Move back — the loot dialog reopens with the same item still listed, meaning `✕` did not actually collect or discard it
- **Expected:** Either `✕` discards the loot (matching "Leave All" semantics) or it should not be treated as a valid way to dismiss the flow without a decision
- **Actual:** The loot stayed pending; "Take All" alone doesn't commit, and I had to explicitly click "COLLECT SELECTED ITEMS" on a later visit to actually clear it
- **Confidence:** Reproduced once, self-caused by test-script sequencing rather than confirmed as something a normal player would hit via the UI (a human player naturally clicks "Take All" then the big collect button) — flagging as low-confidence/UX-adjacent rather than a hard bug
- **Suspected cause:** `✕` on the loot-collection dialog likely just hides it client-side without calling the collect/discard endpoint, leaving server-side loot state untouched until the tile is re-visited and the dialog is regenerated

### Finding 3 — Documented route order collapses the "Ferry Landing declines, then Scene 6 fires on re-entry" test window
- **Severity:** Low (test-plan/documentation note, not a code defect)
- **Location:** `eastern-descent-nomad-camp` (1,2) RiversEdge → (0,2) Water Step
- **Steps to reproduce:** Follow the assignment's own order exactly: Camp Entry (5a) → Devet (5b) → Liss (5c) → Mara (5d)
- **Expected (per assignment):** After Mara's first-contact scene (5d), visiting the Ferry Landing should show the decline line and no beta-end dialog; only after re-entering (1,2) should Scene 6 fire
- **Actual:** `MaraObservationEvent` (Scene 6) fires immediately, chained right after Scene 5d closes, because its `check_conditions` only checks that `MaraFirstContactEvent`, `DevetIntroEvent`, and `LissObservingEvent` gates are all set (`ch03.py:1118-1123`) — and by visiting Devet and Liss *before* Mara (as the assignment's own route does), all three gates are already true the instant Mara's scene ends. There is no re-entry step needed or possible in this order.
- **Confidence:** Reproduced once, but deterministic given the event logic — this isn't probabilistic
- **Suspected cause:** Not a code bug — `MaraObservationEvent.check_conditions()` is working exactly as designed (gate-driven, fires as soon as all three prerequisites are met, regardless of visit order). The assignment/test-plan's assumption that visiting Mara last still requires a "re-entry" is only true if a player visits Mara *before* Devet and Liss. Worth a note to the QA script/primer author: either specify visiting Mara first (to genuinely exercise the decline path) or drop the "declines, then re-entry" framing for the 5a→5b→5c→5d order.

### Finding 4 — Stray "STORY" popup duplicates a tile's own room description
- **Severity:** Low
- **Location:** Observed at `grondelith-mineral-pools` (2,0) Grondelith Entry and `grondia` (7,9) Grondelith Entrance, both on first visits/re-visits
- **Steps to reproduce:** Enter a tile with a fresh (non-story) tile description shortly after an unrelated scene or passage transition; occasionally the description text appears wrapped in a "✨ STORY" modal (with Hold-to-skip / Close controls) instead of only in the normal room-description panel
- **Expected:** Plain room descriptions render only in the exploration text panel, not as a modal "STORY" scene
- **Actual:** At (7,9) this modal reappeared 2-3 times in a row across move attempts, each showing a different segment of the same room description, and had to be closed before movement buttons became clickable again — it silently blocked `Move` clicks until dismissed (which looked like a stuck UI until diagnosed)
- **Evidence:** Reproduced via repeated `aria()` captures in this session's raw transcript at (7,9); no dedicated screenshot taken (deprioritized to preserve budget once the pattern was identified as dismissible)
- **Confidence:** Seen 3+ times, low-severity since it's always dismissible and doesn't lose state, but it does intermittently block movement input until the player (or tester) notices and closes it, which reads as a soft-lock at first glance
- **Suspected cause:** Not investigated in source given time budget; possibly a first-visit "room-entry" narration event that's being routed through the same STORY-modal component used for real story events, rather than the plain exploration panel

## 7. Non-bug observations

- Session's starting HP was 112/112, not the primer's stated 108 — likely a config/loadout detail unrelated to this run; not investigated further since it's cosmetic to the test.
- Two long stretches of this session (the King Slime advisor-guided auto-fight loop and a Talus Hound fight) were run via `run_in_background` Bash automation that hung on Playwright default (30s) click timeouts when a `page.get_by_role("dialog")` locator strategy didn't reliably resolve the intended button — this cost a large share of the tool-call/time budget without any actual game progress (HP stayed flat, combat log unchanged) during those stalls. Switching to direct, unambiguous button selectors (`.nth(1)` on a known 2-button target list, rather than XPath `following::button[1]` sibling lookups) fixed it immediately once diagnosed. Worth calling out for future testers: prefer simple `.first`/`.nth(n)` on `get_by_role` locators inside the SELECT TARGET dialog over XPath-based "find the button near this text" strategies, which are fragile against this app's DOM.
- The King Slime's memory-flash sequence and the multi-beat VN conversations (Votha Krr, Mara, Liss) are considerably longer/richer than the primer's one-line preview quotes suggest — several ran 10-20+ dialogue beats. Budget accordingly if replaying this route.
- Autosave 403 toasts, React Router future-flag warnings, and background-music `NotAllowedError`s were seen throughout and are known noise per the primer — not reported.
- Combat UI is snappy and legible: Tactical Advisor text was consistently accurate (percentages, damage ranges, and the "Rest is critical" / "Dodge is critical" framing all matched what subsequently happened in the log), and the battlefield beat-timeline's "⚠ DEADLY" marker was a genuinely useful, unmissable warning signal for the King Slime's telegraphed attack — this is pillar-3 ("every roll explainable, no unwarned deaths") working exactly as intended.
