## 4. Findings

### Critical — Unresolved passageway-confirmation event + entering combat deadlocks the session permanently
**Location:** `src/api/services/game_service.py` — the `#543` guard at line ~2445 (`process_event_input`, rejects a `PassagewayTransitionEvent` confirm while `player.in_combat`) combines with the "Event pending" guard at line ~3956 (`execute_move`, refuses all combat moves while any non-completed event sits in `pending_events`).

**Steps to reproduce (from a fresh login):**
1. Stand on `eastern-descent` (0,2) "Grondia Eastern Gate". This tile's own "Eastern Gate" object is the *return* passage to Grondia (15,5); interacting with its only keyword, `enter`, queues a `PassagewayTransitionEvent` ("Step through?") — same as any other passage object.
2. **Do not answer it yet.** Move east to (1,2) "High Ledge". A Rock Rumbler here has a real chance to aggro on entry (`combat_started: true` in the move response).
3. With combat now active, try to resolve the still-pending "Step through?" event: `POST /api/world/events/input {event_id, user_input: "continue"}` → `400 {"success": false, "error": "Cannot use a passageway while in combat."}`. There is no decline/cancel option in `input_options` (only `"continue"`), and `POST .../events/input {user_input: "cancel"}` is rejected with `"Invalid choice. Please select from: continue"`.
4. Try a combat move instead: `POST /api/combat/move {move_type: "attack", ...}` → `200 {"success": false, "error": "Event pending", "message": "Please resolve the current event before taking combat actions."}`.
5. Both directions are now permanently refused — the event can't resolve because combat is active, and combat can't proceed because the event is pending. `POST /api/world/move` in any direction returns `"Cannot move while in combat"` too. Verified this holds across 3+ retries; no escape route found within the primer's documented API surface (only `/api/debug/*` would break the lock, and the brief says not to use it to play).

**Root cause, from the code comment itself:** the #543 fix (lines 2436-2442) is explicit that it added the in-combat guard *because* "combat can start... after a confirmation was queued and before the player submits this input" — but the fix only refuses the confirm; it never gives the player a way to *decline* the passage or otherwise clear the now-stuck event, and the pre-existing "Event pending" combat guard (line ~3956) wasn't updated to account for a passageway event that is now provably unresolvable until combat ends, while combat itself can't be resolved because of it. The two guards are individually reasonable and together form a hard lock.

**Impact:** any player who queues a passage confirmation and then walks (or is dragged, e.g. by a companion AI) into a fight before answering it is stuck with no legal action. In practice this is easy to hit by design pattern alone: several tiles have both a return-passage object and an adjacent hostile spawn (the tester triggered it on the very first tile of the Eastern Descent). I recovered by abandoning the session and logging in fresh (a real player would lose all unsaved progress, and `/api/saves` is 403 for test sessions anyway per the primer, so in production this would cost real save progress up to the last autosave tick).

**Confidence:** High — reproduced once, deterministic given the steps (not a flaky race; the guard logic is unconditional once both conditions hold).

**Suggested fix direction:** either (a) give `PassagewayTransitionEvent` a `"cancel"`/`"decline"` input option so it can be cleared without moving, independent of combat state, or (b) auto-cancel a pending, not-yet-confirmed `PassagewayTransitionEvent` the moment combat starts (mirroring how the #543 fix already treats combat as authoritative over the passage), rather than leaving it queued and unresolvable.

### Low / tester-process note — `/api/combat/move` cooldown only drains on a move that itself spends beats
Not filed as a game bug, but worth recording since it cost real debugging time and could trip up another automated tester: `move_type: "attack"` when `Attack` shows `"available": false, "reason": "Available in N beats"` fails with `"Move not ready yet"` and — critically — repeatedly sending the free, 0-beat `"Check"` move (`stage_beats` all 0) does **not** decrement that cooldown; only a move with nonzero `stage_beats` (e.g. `"Wait"`, which itself needs a follow-up `number_input` for duration) advances the clock. The primer's guidance ("only becomes available when a different move spends beats") is correct, but "any other move" isn't quite right — it must be a move that consumes beats, not a free utility action. First attempt at automating combat looped ~150 calls against a fully-healthy player without landing a hit before this was diagnosed.

### Observation — blind automated `number_input` handling is risky mid-combat
While building an automated combat solver, sending a blind numeric answer (`move_type: "number"`) to whatever `number_input` prompt was currently open worked correctly for "how many beats to Wait," but the same code path is also used for other numeric prompts (e.g., a "Use Item" quantity/index selection, per the route docs' generic `number_input` contract). Inventory before/after the run shows one `Restorative` potion vanished (2 → 1) with no corresponding "used potion" narration captured in this tester's log; this is most likely this tester's own blind automation misfiring on an unrelated `number_input` prompt rather than a game bug, but I can't rule out an engine-side issue and didn't have budget to isolate it. Flagging so it isn't silently attributed to combat loot logic.

### Observation — `collect-loot` reports empty `collected: []` even when items were dropped
On every post-victory `POST /api/combat/collect-loot` this run, the response was `{"collected": [], "events_triggered": [], "skipped": []}` even when the preceding `combat_active: false` status/end_state clearly listed `items_dropped` (gold, potions, a Longsword, etc.) and those items *did* land in `/api/inventory` moments later. Functionally correct (nothing was lost), but the `collected` field never reflecting what was actually collected is confusing telemetry for a client built against this contract — worth a look, not filed as a bug since gameplay was unaffected.

## 8. Non-bug observations

- Rock Rumbler and Talus Hound aggro on tile entry appears deterministic-per-tile-visit rather than a coin flip across repeated visits in this run (every hostile-tagged tile triggered combat exactly once, on first entry) — consistent with "probabilistic" in the sense that different sessions may see different enemy name/seed, but within this one run it read as guaranteed-on-first-visit rather than genuinely random per attempt. Worth another tester confirming with a second full lap if that distinction matters.
- The Eastern Gate's `action_aliases` (`go`, `leave`, `exit`, `eastern`, `gate`, `east`) are not honored by `/api/world/interact`'s `action` field — only the object's real `keywords` array (`enter`) works. Likely intentional (aliases may be for a different, text-parser-style entry point not used by this API), but worth a one-line confirmation from someone who knows the intended contract.
- Votha Krr's dialogue choice in this run (option "b", "What is this thing, exactly?") led to a distinct explanatory branch culminating in "Go now. Seek the Echoing Caves to the west, beyond the river." This is west of the Eastern Descent, i.e., different content than the Eastern Descent/Nomad Camp route this leg covers — noted as pure flavor/lore, not a routing bug, since the Eastern Gate still opened and led where the brief expected.
