## 4. Findings

### Finding A — Critical — King Slime victory scene delivered by `GET /combat/status` AND duplicated by `collect-loot` (#683 regression)

**Location:** `src/api/combat_adapter.py` / `src/api/routes/combat.py` (`get_combat_status`, `collect_loot`)

**Steps from login:**
1. Login A1 on :5002, play to the Grondelith Arena (2,6), fight King Slime via repeated `POST /api/combat/move {select_move_and_target, Attack/Advance/Rest}`.
2. The fight's final `POST /api/combat/move` reports `battle_state.status: "victory"`.
3. Immediately call `GET /api/combat/status` (no `collect-loot` yet).
4. Call `POST /api/combat/collect-loot {}`.

**Expected (per #683):** the victory/memory-flash scene appears **only** in step 4's `events_triggered`, exactly once; step 3 must not carry it.

**Actual:** step 3's response already contains `events_triggered: [AfterDefeatingKingSlime, Ch02KingSlimeMemoryFlash]` (both fully populated, with prose). Step 4's response then contains **the same two events again**, byte-for-byte identical `output_text`.

**Evidence** (from `logs/qa/api-runs/A1_api.jsonl`, both calls at `17:20:45`):
```
GET /api/combat/status  → combat_active:false, end_state.status:"victory",
                            events_triggered: ["AfterDefeatingKingSlime","Ch02KingSlimeMemoryFlash"]
POST /api/combat/collect-loot → events_triggered: ["AfterDefeatingKingSlime","Ch02KingSlimeMemoryFlash"]  (identical)
```
Resolving the surviving pending event afterward (`Ch02KingSlimeMemoryFlash`, needs_input) worked normally and did not re-fire, so the *player-visible* end state is probably fine (the frontend likely only renders whichever response it processes first) — but the API contract #683 exists specifically to prevent this leak-and-duplicate pattern, and it is reproducing here exactly as described in the issue.

**Confidence:** High — this is a direct capture from the real API/session, not a simulated repro.

**Note on my own methodology:** I did not perform the primer's literal "GET twice, then collect-loot" sequence (I made one post-victory GET, inside a generic combat-poll loop, followed immediately by collect-loot). The evidence above is nonetheless dispositive: even a single GET after victory already leaked the scene, and collect-loot then repeated it — which is a stronger, not weaker, demonstration of the regression than the prescribed sequence would have produced.

### Finding B — Medium/Observation — Fatigue exhaustion can leave the player action-locked mid-fight with only Wait

**Location:** combat move economy / advisor (relates to known #700)

**Steps:** Default new-game start, fight the first 5-enemy Grondelith Channel Entry pack (3 slimes, a Stone Creature, a 5th slime) using only Attack/Advance (no Rest). By turn ~15 fatigue hit 0; `Attack`, `Dodge`, `Shoot Bow/Crossbow`, and `Crusader's Oath` all reported `available: false, reason: "Not enough fatigue"`; `Advance` reported `"No one is out of reach"`. The only available combat move was `Wait` (and `Rest`, which I hadn't tried yet), so a naive loop that doesn't know to `Rest` stalls and eats free damage every beat — this run ended in Jean's death (`end_state.status: "defeat"`) purely from unanswered incoming damage while stuck on `Wait`.

**Not a bug per se** — `Rest` is available and does restore fatigue mid-fight (confirmed in the replay: `Rest` → `Attack` alternation cleared the same enemy composition without incident). But the reason strings never suggest `Rest` as the way out, and this compounds the already-known #700 (advisor can recommend moves that overshoot the beat window) — an unguided player who doesn't know `Rest` works mid-combat has no obvious next move once fatigue bottoms out. Recommend: when every offensive/defensive move is unavailable purely for `"Not enough fatigue"`, surface `Rest` more prominently (e.g., in the advisor's `suggested_moves`).

**Confidence:** Medium — confirmed via two live playthroughs (one death, one clean recovery via `Rest`), but I did not inspect the advisor (`suggested_moves`) payload directly to confirm it truly never proposes `Rest`.

### Finding C — Low/Observation — Regular-mob fights consistently return empty loot

**Location:** loot tables for Grondelith slimes / cave bats / eastern-descent talus hounds

Every `collect-loot` call after a non-boss fight (roughly 8 fights total across Mineral Pools and Eastern Descent) returned `{"collected": [], "events_triggered": [], "skipped": []}` with `success: true` — no error, just nothing. Only King Slime himself dropped anything (99 gold, via the `AfterDefeatingKingSlime` narrative text — no separate loot line). This may simply be the intended loot table for these enemies (trash mobs with 0% drop rate), but it's worth a design confirmation since it means the whole Mineral Pools gauntlet nets the player nothing but EXP.

**Confidence:** Low — could easily be correct-by-design.

### Finding D — Low — `object_state.locked` doesn't reflect the Eastern Gate's actual lock state

**Location:** `src/objects.py` `Passageway` (Eastern Gate) serialization

Both the refused interact (gate still sealed, before Votha Krr) and the successful interact (gate open, after Votha Krr) returned `object_state: {"locked": false, ...}`. The field never flips to `true` even while the gate is actively refusing passage, so a client can't use it to pre-emptively grey out the "enter" affordance — it has to attempt the interaction and read the message. Cosmetic/API-completeness issue, not a blocker.

**Confidence:** Medium (observed directly, both states).

### Finding E — Low — A pending event followed the player across a map transition and later teleported them backward

**Location:** event lifecycle / `pending_events` across map boundaries

**Steps:** At Grondia (7,5) the `Ch02GuideToCitadel` event began (`needs_input: true`). I moved on to interact with other things without resolving its final "Continue" prompt, then walked all the way to the Grondelith Entrance and stepped through into the Mineral Pools map. `GET /api/world/events/pending` on the new map still listed the same unresolved `Ch02GuideToCitadel` event (a *second, differently-worded* variant of the guide scene, itself an interesting non-bug variance). Resolving it there caused `where()` to report the player back in **Grondia** at (12,4) — i.e., completing a stale Grondia-scene event while standing in the Mineral Pools teleported the player back to Grondia, undoing the map transition.

**Assessment:** likely only reachable via the API (the web frontend probably blocks movement while a `needs_input` event is outstanding), so this may not affect real players. Flagging because it's a genuine state inconsistency: an event object should either be scoped/invalidated on map change, or the API's move endpoint should refuse to let the player leave a tile with a pending blocking event, matching whatever the frontend enforces.

**Confidence:** Medium — one clean repro; did not attempt to reproduce a second time (would have cost combat/time budget).

## 6. Non-bug observations

- The `Ch02GuideToCitadel` scene text varies between playthroughs/entry points (two distinctly different scripted variants were observed for what is nominally "the same" scene) — good replay variety, not a bug.
- Several story beats that read like they should be blocking, multi-choice conversations (`GorranGestureEvent`, `MaraFirstContact`, `DevetIntro`, `LissObserving`, `MaraObservation`) are actually delivered as single non-blocking `events_triggered` payloads folded into the triggering move/interact response, with the *entire* multi-beat conversation pre-resolved server-side (no player choices consumed). This makes the API route feel more like "cutscene delivery" than "dialogue tree" for these — fine for a beta pass, worth knowing if a future tester expects `input_type: choice` prompts here and doesn't see any.
- Attribute point allocation was entirely manual test-tester judgment (I dumped everything into Endurance/Strength for a straightforward melee-tank build); this is not something the API validates against any "optimal" build, as expected.
- Party composition: Gorran is absent (`party_members: []`) for the entire Mineral Pools stretch (by design, per CLAUDE.md's "Jean fights the Mineral Pools WITHOUT Gorran"), then reappears immediately after the King Slime victory event resolves.
