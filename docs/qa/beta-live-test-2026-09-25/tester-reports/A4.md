## Findings

### Finding 1 — Critical: DevetIntroEvent and IronAndOathIntroEvent never fire, blocking the end-of-beta ferry scene
- **Location**: `src/story/ch03.py` — `DevetIntroEvent` (fires on first entry to FireRing (3,2)), `IronAndOathIntroEvent` (fires on first entry to Tradepost (4,3))
- **Steps from login**:
  1. Login A4 on :5004, navigate to Nomad Camp via Eastern Gate → Eastern Descent → Camp Entrance (all as documented above).
  2. Enter FireRing (3,2) tile for the first time via `POST /api/world/move {"direction":"south"}` from Supply Tents (3,1). Response: `events_triggered: []`.
  3. Confirmed via `GET /api/world/events/pending` immediately after: `{"events": [], "success": true}`.
  4. Left and re-entered the tile (north, then south) — still `events_triggered: []` both ways.
  5. `talk` on Devet directly gives only a generic idle line ("Devet glances at Jean's pack. Then at the fire. 'Long road,' he says...") — never the scripted intro conversation.
  6. Same pattern at Tradepost (4,3): first entry via `southeast` move, `events_triggered: []`, `pending_events: 0`. Left/re-entered (west/east) — still nothing. `talk` on Kaelen gives only a generic flavour line, never the 5-beat IronAndOathIntroEvent scene.
  7. By contrast, `LissObservingEvent` at CampFarEdge (3,4) **fired correctly** on first entry via the same mechanism (`northeast` move from FireRing), full staged conversation delivered in `events_triggered[0].output_text`. This rules out a blanket "no tile events fire" bug and isolates it to these two specific events.
  8. Read `src/story/ch03.py:1189-1213` — `MaraObservationEvent.check_conditions()` requires `PREREQUISITE_BEATS = (MaraFirstContactEvent, DevetIntroEvent, LissObservingEvent)` gates ALL set. Since `devet_intro_done` never gets set, `MaraObservationEvent` (which sets `Passageway.DEMO_END_READY_FLAG`, the ferry-ready gate) can never fire.
  9. Confirmed downstream effect at WaterStep (0,2): `POST /api/world/interact {"target_id": "<Ferry Landing>", "action": "enter"}` returns `beta_end: true` but with message **"Jean stops at the ferry landing and looks at what lies beyond. The way is plain enough — but not today."** — a placeholder refusal, not Mara's intended ferry-departure scene.
- **Expected**: DevetIntroEvent and IronAndOathIntroEvent each fire once on first tile entry (skipdialog=False on this config), same as LissObservingEvent did. Eventually MaraObservationEvent fires and the beta ends with the proper ferry-departure narrative.
- **Actual**: Both events never fire (has_run stays false, no exception surfaced to the client — consistent with the documented "exceptions inside tile events are swallowed" behavior in `.claude/rules/api-layer.md`), so the beta's climactic scene chain is short-circuited into a generic "not today" refusal.
- **Confidence**: High. Reproduced from a clean tile entry, retested with re-entry, and cross-checked against a working sibling event (Liss) and the source-level gate dependency chain.
- **Suspect file:line**: `src/story/ch03.py:581-666` (DevetIntroEvent), `src/story/ch03.py:834-` (IronAndOathIntroEvent), `src/story/ch03.py:1189-1213` (MaraObservationEvent's gate on the above two).

### Finding 2 — High: Anvil `pet` before any interaction returns fully generic fallback text (#695 partial fix not verified)
- **Steps**:
  1. First arrival at Tradepost (4,3), before talking to Kaelen/Vespera/Anvil at all: `POST /api/world/interact {"target_id": "<Anvil>", "action": "pet"}`.
  2. Response: `"message": "Jean successfully completes the 'pet' action."` — the engine's literal generic fallback string, not any Anvil-specific flavour text.
  3. After subsequently talking to Kaelen (flavour line only, not the full scene) and to Anvil (`talk`, which DID give an Anvil-specific line: "Anvil's sensory stalks swing toward Jean..."), a second `pet` call gave a proper Anvil-specific line too ("A sharp hiss vents from the shell...").

- **Actual**: The very first, ungated `pet` call returns the literal generic fallback, not a flavour line.
- **Confidence**: High for the literal first-call behavior observed; note this is entangled with Finding 1 (IronAndOathIntroEvent never fires, so "before/after Iron & Oath" as a state can't be cleanly isolated — but AnvilIntroEvent's own gate description in `src/story/ch03.py:1018-1036` says Anvil's `talk`/`pet` set `CONVERSATION_READY_FLAG` on first use independent of the full scene, so the first-ever `pet` call is the correct target for this check regardless).
- **Suspect file:line**: `src/story/ch03.py:1018-1036` (AnvilIntroEvent docstring/gate) and wherever Anvil's `pet`/`talk` NPC methods live (`src/npc/` — not located exactly, ran out of budget to trace further).

### Finding 3 — Low/Observation: `npc/chat/open` rate-limited mid-session
- After ~6 chat-open calls in quick succession (Jambo, Liss, Mara, Devet, Kaelen), `POST /api/npc/chat/open {"npc_id":"Vespera"}` returned `429 {"error":"rate_limited"}`, and a retry a call later and a subsequent Anvil chat-open also 429'd. This is plausibly an intentional per-session rate limiter rather than a bug, but it meant Vespera's and Anvil's chat mechanics could not be exercised. Not filed as a bug — flagging for awareness since it silently blocked test coverage of two named NPCs the assignment called for.

### Finding 4 — Observation: combat move API ergonomics (not a bug, just a documentation trap I fell into)
- `move_type: "move"` with `move_id: "8"` (Attack) returns `success:true` even when the target is out of range (`in_range:false`); it silently consumes a beat with no visible effect (no damage, no distance change, no error). A caller polling status without checking `in_range` explicitly can loop indefinitely believing Attack is progressing. This matches the primer's own warning ("if you catch yourself sending the same request 10+ times, stop and read input_type") but the specific trap here is that `available:true` does NOT imply "will have an effect" — it should probably also require the target being in range, or the response should carry a clearer no-op signal. Not filing as a bug since Advance is available and the fix is in "read input_type/in_range", but note this cost real tool-call budget during testing and could confuse players too if the frontend doesn't disable Attack when out of range.
