## 3. Fix verification

### #683 — King Slime victory scene via collect-loot, not consumed by GET
**PASS.** After King Slime died:
- `GET /api/combat/status` (1st call): `events_triggered` contained
  `AfterDefeatingKingSlime` + `Ch02KingSlimeMemoryFlash` (full prose captured).
- `GET /api/combat/status` (2nd call): **identical** `events_triggered` payload — the GET did not
  drop or duplicate the held events.
- `POST /api/combat/collect-loot`: same 2 events delivered, exactly once in that response.
- A 3rd `GET /api/combat/status` afterward: `events_triggered: []` — the hold was cleared, and a
  second `collect-loot` call also returned `events_triggered: []` — no re-delivery.
This matches `GameService._held_post_combat_events` (non-consuming, used by GET status) vs.
`_take_post_combat_events` (consuming, collect-loot only) at `src/api/services/game_service.py:4393-4407`.
By design, GET *echoes* the held scene (so it isn't lost if a caller doesn't relay it — see the
docstring at `src/api/services/game_service.py` around line 4295), but it never removes it from
what collect-loot ultimately delivers, and collect-loot's own delivery is exactly-once. This
satisfies the fix's contract even though the scene is visible via GET as well as collect-loot —
worth a frontend sanity check that a 3-second status poll before the player clicks "loot" doesn't
re-render the cutscene each poll (out of scope for this REST tester; noted as an observation).

### #691 — Advance reports "no opponents", not a generic failure
**PASS.** Right after triggering the King Slime encounter but before the King Slime combatant was
fully loaded into `battle_state.combatants` (the very first status snapshot, `combat_active:
false`, combatants list held only the stale player record from the previous fight), `Advance`'s

This matches `Advance._unavailability_code()` in `src/moves/_movement.py:222-235`, which returns
`UnavailableReason.NO_OPPONENTS` specifically when `combat_proximity` is empty (the #691 fix), vs.
the old generic `ALREADY_ADJACENT`. I could not reliably force the mid-fight "enemy just died"
timing window via HTTP (each attempt to probe exactly at the kill frame either landed after
`combat_active` had already flipped false — "Not in combat" — or the position/proximity map was
already populated by the time the response arrived), so this is verified via the pre-combat-init
snapshot plus source reading rather than the exact "an enemy dies mid-fight" framing. The message
itself is correct wherever observed.

## 4. Findings

### #690 (FAIL) — `POST /api/saves` on a dead player returns the generic test-session 403, not a death-specific message
- **Severity:** Medium
- **Location:** `src/api/routes/saves.py` (saves POST route), likely `src/api/services/*save*`
- **Steps:**
  1. Login as A2b on `api0925` (:5002), allocate level-up points, walk to Grondelith Entrance,
     enter the pools.
  2. Fight repeatedly without resting/healing/dodging until `end_state.status == "defeat"`
     (`Grondelith Deep East`, round 3 of the final encounter).
  3. `POST /api/saves {"name": "test"}`.
- **Expected:** Per the primer/#690, a 403 with a **death-specific message**, distinguishable from
  the generic "no `db_user_id`" test-session 403 that every test session gets regardless of player
  state (`CLAUDE.md`/`.claude/rules/api-layer.md`: *"`/api/test/session` creates a session with no
  `db_user_id`... the 'no db_user_id' 403 branch... is only reachable through this bypass"*).
- **Actual:** `{"error": "Cloud saves require a registered account.", "success": false}`, 403 — the
  exact same message a *living* test-session player gets when trying to save. There is nothing in
  the response that says Jean is dead.
- **Confidence:** High (direct evidence: response body quoted above; the message text names no
  death state and is the standard no-account-registered message).
- **Suspect file:** `src/api/routes/saves.py` — the POST `/api/saves` handler evidently checks
  `db_user_id` before (or instead of) checking `player` death state, so a dead test-session player
  never reaches whatever branch would emit the death-specific 403 the primer describes.

## 6. Non-bug observations

- After the level-up-points briefing, the guide-to-citadel scripted walk **teleports** Jean from
  the Grondelith Entrance area straight to the Ecumerium (11,5) mid-conversation — expected
  (matches the prose: "the passages widened... east into the city"), but it means a route script
  that assumes tile-by-tile continuity after this event needs to re-read `where()` rather than
  trust its last known position.
- Mineral Pools spawner tiles (`NPCSpawnerEvent`/`PulsingGlandEvent`) are one-shot per tile per
  session: revisiting a cleared tile multiple times (tested at (2,2)/(2,3) three times each)
  triggered no new encounter. After King Slime dies, the entire Pools area is fully cleared (no
  hostile NPCs anywhere) — consistent with Votha Krr's "remove [the heart], and the rest will
  follow" framing.
- `#683`'s held post-combat events are, by design, echoed (non-destructively) on every
  `GET /api/combat/status` poll between victory and `collect-loot`. This is intentional
  (`src/api/services/game_service.py` docstring near line 4295) so a caller that doesn't relay the
  move-response events doesn't lose them, but it does mean the frontend must dedupe/guard against
  re-showing the victory cutscene if it renders directly off a status-poll response before the
  player clicks to collect loot. REST-only, so I could not check the frontend's actual behavior —
  flagging for the browser tester.
