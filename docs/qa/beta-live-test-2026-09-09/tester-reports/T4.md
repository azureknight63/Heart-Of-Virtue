## Findings

### Finding #1 — CRITICAL: Page reload/navigation gets the exploration UI permanently stuck replaying a stale combat log

- **Severity**: Critical (route blocker on the client; engine state is unaffected)
- **Location**: `eastern-descent-nomad-camp` map, tile `(1,2) Rivers Edge` (client-observed; likely reproducible anywhere after any prior combat in the session)
- **Steps to reproduce**:
  1. Play through at least one combat encounter to completion (I had fought 3: Rock Rumbler Toga, Rock Rumbler Tisoteix, 2× Talus Hound).
  2. Continue exploring afterward (I moved several more tiles, entered the Nomad Camp map, ran two more story scenes).
  3. Reload the page (`page.reload()`), or fully navigate to the same game URL (`page.goto(...)`).
  4. Observe the UI.
- **Expected**: Reload shows the current exploration screen (`Rivers Edge`, Mara/Gorran present), matching `where()`/`/api/status`.
- **Actual**: The UI renders the **Combat** screen instead, showing a `RESOLVING BATTLE…` banner and slowly replaying the entire combat log from a fight that ended ~10 minutes and 3 combats earlier (log lines from `13:37:43` through `13:48:38` replay one at a time over multiple seconds each, never reaching the end). Confirmed via `GET /api/combat/status` → `combat_active: False` and `where()` → correct tile (`Rivers Edge`), i.e. **the engine is correct; only the client is stuck.** Reproduced identically across three separate triggers: `page.reload()` (twice) and `page.goto()` (once) — each restarted the same replay from a similar point.
- **Evidence**: `all_errors()` showed no new console/network errors beyond the known-noise autosave 403s; the stuck rendering is a pure frontend state bug, not a request failure.
- **Confidence**: Reproduced 3× in this session. **Caveat on repro path**: to conserve tool-call budget after a lengthy combat, I advanced position for one hop (Tradepost → Rivers Edge) via direct `POST /api/world/move` calls rather than the in-game movement UI (as the primer allows for verification). It is possible — though I could not rule it out given budget — that bypassing the UI's own movement flow contributed to the desync (e.g., a client-side "last active combat" cache never being cleared because the UI's own transition-out-of-combat code path didn't run). A player who never leaves the UI's own controls may or may not hit this. **Recommend the orchestrator re-verify with UI-only navigation** (no direct API calls) before filing as confirmed-in-normal-play, but given engine/UI state fully diverged and three independent reload attempts all reproduced it, this should not be dismissed as a fluke.
- **Impact**: If this generalizes to normal play, a mobile player who reloads their browser (common on mobile — backgrounding, memory pressure evicting the tab, accidental pull-to-refresh) after any combat could lose the ability to continue playing without restarting their session entirely (no ability to save in a test session; a real registered account might not fare better if the bug is genuinely a stale-cache issue rather than a test-session artifact).

### Finding #2 — HIGH: Portrait conversation dialogs can render below the visible viewport with no scroll affordance, on the phone viewport

- **Severity**: High
- **Location**: Multiple story scenes on `eastern-descent-nomad-camp`: Camp Entry (3,0) Jean/Gorran/Liss scene; Tradepost (4,3) Jean/Gorran/Kaelen/Vespera/Liss scene
- **Steps to reproduce**:
  1. Trigger a scripted story scene with 3+ speaking portraits on the 375×812 mobile viewport.
  2. Advance to a stage where the dialog stacks multiple portrait cards (2-column grid) above the spoken line and the Continue/CLOSE control.
  3. Measure element positions against `window.innerHeight` (812).
- **Expected**: All interactive controls (CLOSE / Continue) and the actual spoken line remain reachable/visible, or a visible scroll indicator (the room panel elsewhere in this build shows one: `▼ scroll ▼`) tells the player there's more below.
- **Actual**: Measured directly via `getBoundingClientRect()`:
  - Camp Entry, 2-portrait scene (Jean+Gorran): `CLOSE` button at `y: 869–913` vs viewport height `812` — **entirely off-screen**. Two consecutive `touchscreen.tap()` calls at the button's reported coordinates did nothing (confirmed via `hit_test`: empty hit-stack at that point, since it's outside the physical screen). Required `scroll_into_view_if_needed()` to reach it.
  - Tradepost, 5-portrait scene (Jean/Gorran/Kaelen/Vespera/Liss): the **spoken dialogue text itself** ("That girl's got more nerve than sense...") measured at `top: 880.4, bottom: 1008.4` — completely below the 812px fold. Screenshot T4_023 shows only portrait cards on screen; the actual line being spoken and every control are invisible. Reproduced the same CLOSE-button-off-screen pattern here too (`y: 869`).
  - Nowhere in either scene's visible viewport does any scroll hint appear — the `▾ Click, Space or Enter to continue` prompt text exists in the DOM but is likewise scrolled out of view.
- **Confidence**: Reproduced twice, in two different scenes with different portrait counts (2 and 5), both times measuring the same class of overflow (~55–95px past the fold).
- **Note on the #541 fix**: the underlying #541 defect (fixed two 150px columns squeezing text into ~36px) is genuinely fixed — see Fix Verification below — this is a **new, related** overflow problem that only appears once enough portraits stack vertically to exceed one screen's height. It is a regression risk of the same layout area, not the same bug.
