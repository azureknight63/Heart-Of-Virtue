## 4. Findings

### Driver/automation stability — two full deadlocks (not a game bug, but blocks coverage)
- **Severity**: N/A for the game (tooling issue) — flagging because it explains the incomplete tile table.
- Twice during this run, a `qa.py exec` call that chained UI clicks with `page.reload()` while an event was mid-resolution caused the driver's Playwright worker thread to become permanently unresponsive (`## ERROR / timeout waiting for browser thread`); only the `/ping` health check kept responding, everything else queued forever. Recovery required `taskkill //T //F` on the driver PID and a fresh `qa_driver.py` launch (new session each time, back at (1,2)).
- Confidence: reproduced twice, both times shortly after I combined `resolve_pending_via_api()` (a raw API POST to `/api/world/events/input`) with an immediate `page.reload()` while the frontend's own event dialog was still open on the same event. This is very likely a **test-harness-induced** condition (racing the UI's own event fetch against a script-driven API resolution), not something a normal player would hit by clicking through the UI alone.

### Frontend event-input retry storm on a stale event_id (Medium, induced by the above race — flagging anyway)
- **Location**: any tile with a story/loot event, observed at (10,4)/(11,3) archive-entry flow.
- Once the race above put the frontend's cached `event_id` out of sync with the server, the UI's `fetchWithRetry` (`useEventManager.js`) retried the same expired `event_id` against `POST /api/world/events/input` **dozens of times over more than 2 minutes**, each attempt getting a `400 {"error":"Event <id> not found"}`, with no visible user-facing indication and no apparent retry cap for a clearly non-transient (400, not 5xx) error.
- Expected: a 400 "not found" is permanent — the client should stop retrying and/or resync (e.g. re-fetch `/api/world/events/pending`) rather than spinning.
- Actual: continuous console-error/network spam (seq 34–167 in this session, `13:53:16`–`13:59:29`) until it eventually self-terminated.
- Confidence: seen once, self-induced by concurrent API+UI event manipulation from the test script. Flagging because the *lack of a retry cap on a 400* is a real robustness gap even if the trigger here was artificial — worth a look, not a confirmed player-facing bug.

### Raw backend error string rendered inside the STORY dialog (Low, low confidence)
- **Location**: `grondia-conclave-archive (2,2)`, entering via the Archive Door at (11,3).
- During the same race, the STORY dialog at one point rendered: `paragraph: Event 01fbb83d-4211-41ec-bb63-4e824a12670b not found` directly in the narrative dialog, with the "Step through" button then permanently disabled until a page reload.
- This is a raw API error string surfacing in player-facing UI — in spirit similar to (but not literally) the class of bug #553 closed. Not filing as equivalent-severity because it required my own script's concurrent API call to trigger; a normal single-session player driving only through the UI is unlikely to desync their own `event_id` this way.
- Confidence: seen once, low confidence as a genuine player-reachable path.

### Minor: INVENTORY accessibility-tree text order is misleading, but the visual UI is correct
- Not filing as a bug. The flattened accessibility-tree/`innerText()` dump lists `"Shortsword ... EQUIPPED Rusted Iron Mace ..."`, which reads as if Shortsword carries the badge. A screenshot (`T2_002_inventory_check.png`) confirms the `EQUIPPED` pill is visually attached to the **Rusted Iron Mace** card, not the Shortsword — the DOM/AOM ordering just doesn't match the CSS grid layout. Noting this only so a future tester doesn't misread the same flattened dump and file a false loadout regression.
