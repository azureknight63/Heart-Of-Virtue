## Findings

### Finding 1 — Unskippable full-screen "LEVEL UP" modal blocks the initial view on session start
- **Severity**: Medium (blocks first look at the game, but has a working escape route)
- **Location**: Grondia (15,5), session start
- **Steps to reproduce**: Start a fresh T4 session on `legb` (mobile viewport) and take the very first screenshot.
- **Expected**: The stated starting scene (Gate East, room description) is what a fresh phone session should show.
- **Actual**: A "⭐ LEVEL UP — Available Points: 66 — Must spend all points to continue" modal fully covers the screen (screenshot `T4_001_01_grondia_initial.png`). It is dismissible by tapping RANDOMIZE (auto-allocates and closes), so it isn't a soft-lock, but a player has no way to see the room, read the intro text, or even understand why they're being asked to spend 66 points before they've done anything.
- **Evidence**: `T4_001_01_grondia_initial.png`. Resolved via `page.touchscreen.tap()` on RANDOMIZE at (281, 468) — confirmed via ARIA dump that the dialog was gone afterward.
- **Confidence**: Seen once, but this is the very first thing every fresh test session on this stack encounters, so it is not an edge case — possibly a harness/seed artifact (level 10 start with unspent points) rather than a real player-facing bug. Flagging so the orchestrator can decide if it's in scope.

### Finding 2 — Movement d-pad buttons are 40x40 CSS px (under the 44px minimum)
- **Severity**: High (violates the project's own documented mobile pillar: "44px touch targets")
- **Location**: Grondia (15,5) and everywhere else, MAP tab movement d-pad
- **Steps to reproduce**: Any tile, MAP tab, measure any `Move <direction>` button.
- **Expected**: ≥44x44 CSS px per `CLAUDE.md`'s "Retro terminal, web-native, mobile-playable" pillar.
- **Actual**: All 8 directional buttons measured exactly 40x40 CSS px:
  ```
  Move North/South/East/West/NE/NW/SE/SW: {x, y, "width": 40, "height": 40}
  ```
- **Evidence**: Bounding-box dump above; visible in `T4_003_03_grondia_map_tab.png`.
- **Confidence**: Reproduced (measured directly via `bounding_box()`, deterministic CSS value, not a rendering artifact).

### Finding 3 — Modal "✕" close buttons are ~26x41 CSS px (under 44x44) across every dialog
- **Severity**: Medium
- **Location**: Every modal (ATTRIBUTES, PARTY, INVENTORY, SKILLS, COMMANDS, INTERACT, SETTINGS, Account, event dialogs) — same shared header component.
- **Steps to reproduce**: Open any panel, measure the "✕" button in the top-right of the header.
- **Expected**: ≥44x44 CSS px close target.
- **Actual**: Consistently ~26x41 CSS px, e.g. ATTRIBUTES panel: `{"x": 318.8, "y": 59.6, "width": 26.0, "height": 41}`. Every panel does have a full-width, correctly-sized secondary close button at the bottom (CLOSE SHEET / Close / CLOSE BOOK / DISMISS), so this is not a hard blocker, but the primary, most-discoverable close affordance is undersized on every dialog in the game.
- **Evidence**: Bounding box dumps for ATTRIBUTES, INVENTORY panels.
- **Confidence**: Reproduced across at least 4 distinct dialogs.

### Finding 4 — CRITICAL: 4 of 5 combat move categories (OFFENSIVE, MANEUVER, INVENTORY, DEFENSIVE) cannot be opened by touch or click on the phone layout; only MISC works
- **Severity**: Critical (makes combat unplayable via the UI on a phone — you cannot attack, defend, maneuver, or use inventory items during a fight)
- **Location**: Any combat encounter, COMBAT tab, phone viewport (375x812)
- **Steps to reproduce**:
  1. Enter any combat on `legb` at 375x812 with mobile emulation.
  2. On the COMBAT tab, attempt `page.get_by_role("button", name="OFFENSIVE", exact=True).click()` (or the touch-equivalent `page.touchscreen.tap()` on its bounding-box center).
  3. Observe the click/tap times out with Playwright reporting `<div>...</div> intercepts pointer events`; nothing happens in-game (no dialog opens, no network request fires).
  4. Repeat for MANEUVER, INVENTORY, DEFENSIVE — all fail identically. MISC (bottom-left position) is the only one of the five that opens.
- **Expected**: All 5 category buttons should open their move sub-panel on tap, same as MISC does.
- **Actual**: `document.elementFromPoint()` at OFFENSIVE's center resolves to the decorative "Hero Heart" portrait wrapper `<div>` (`flex:1 1 0%; display:flex; ...; position:relative` — no z-index), not the button itself, even though the button visually renders on top with `z-index: 5`. The wrapper's bounding box is `{x:16, y:82, w:343, h:322}`, which geometrically overlaps all 4 radially-positioned category buttons (each ~70x44px, `position:absolute`). Only MISC's position falls outside that rect, which is why it alone is clickable. This reproduced identically for both a real `click()` and a real `page.touchscreen.tap()` — confirmed with exact coordinates, so it is not a Playwright quirk.
- **Evidence**:
  - `T4_022_22_offensive_blocked.png`, `T4_023_23_offensive_touch_blocked.png`
  - Playwright error: `<div>...</div> intercepts pointer events` (retried 20x, still blocked)
  - `elementFromPoint` JS probe returning the heart-wrapper div, computed `pointer-events: auto` on it (the decorative heart image itself correctly has `pointer-events: none`, but its containing flex wrapper does not)
  - Click-success matrix: `{"OFFENSIVE": "FAIL", "MANEUVER": "FAIL", "INVENTORY": "FAIL", "MISC": "OK", "DEFENSIVE": "FAIL"}`
  - Because the UI was unusable, both Rock-Rumbler and Talus-Hound fights in this run were driven via `POST /api/combat/move` directly, per the primer's documented fallback for a UI that is "truly stuck."
- **Confidence**: Reproduced across 2 separate combat encounters (Rock Rumbler, Talus Hounds x2), with both `click()` and `touchscreen.tap()`. This is deterministic, not a fluke.
- **Note**: MANEUVER contains "Withdraw" (the flee move's UI entry point), so fleeing combat is also unreachable by touch on this layout — a player who gets into a fight they can't win on a phone has no in-UI way out.

### Finding 5 — CRITICAL: VN-style event/story-scene dialogue text collapses to ~36px wide (one word per line) on phone
- **Severity**: Critical (directly contradicts the stated design pillar: "readable line lengths in dialogue panels")
- **Location**: Any staged story event using the portrait "conversation stage" component — reproduced at Grondia (Eastern Gate departure narration) and the Nomad Camp entry/greeting scene and MaraFirstContactEvent.
- **Steps to reproduce**: Trigger any multi-beat scripted story event with 2 named speakers (e.g., walk into the Nomad Camp for the first time, or approach Mara at (1,2)) on a 375px-wide viewport.
- **Expected**: Dialogue text should occupy the majority of the dialog's width, wrapping at a readable line length (par. CLAUDE.md's own pillar).
- **Actual**: Measured via JS: the dialog's content area is 3 flex children:
  ```
  portrait-column (left):  x=41.75, width=150
  dialogue (center):       x=207.75, width=36     <-- text column
  portrait-column (right): x=259.75, width=150 (empty in this scene)
  ```
  Two 150px portrait columns (300px total) inside a 291.5px-wide stage leave only ~36px for the actual dialogue text, so ordinary sentences wrap one word per line and the text column becomes a vertical ticker tape running the full height of the modal (visible in `T4_029_29_greeting_conversation.png`). In the MaraFirstContactEvent reproduction, the situation is worse: Mara's portrait is also clipped by the dialog's right edge, spilling outside the green modal border (`T4_030_30_mara_first_contact.png`).
- **Evidence**: `T4_029_29_greeting_conversation.png`, `T4_030_30_mara_first_contact.png`, JS layout probe above.
- **Confidence**: Reproduced twice, in two different scenes with different NPCs (Gorran-narration scene, Mara scene) — this is a systemic layout bug in the shared `conversation-stage` component, not scene-specific content.
- **Correction / important context**: My first pass through this component made me *suspect* the dialog was also un-dismissable on phone (clicking the ✕, the text, and Enter all appeared to do nothing at Grondia, and only the keyboard `Escape` key — unavailable on a real phone — closed it). On closer inspection at the Camp scenes, this was **not** a soft-lock: these are simply long, multi-beat conversations (I counted 10+ beats in the greeting scene), and each tap/click on the `[data-testid="conversation-stage"]` element does correctly advance one beat; I had simply under-counted the required taps on the first attempt. Repeated tapping (and, on the final beat, a distinct "Close" button) does reliably reach the end. I'm not filing "no touch dismissal" as a separate bug — it works, it just needs patience and there's no progress indicator ("beat 3 of 11") to tell the player how much is left, which is a minor UX nit, not a blocker.

### Finding 8 — GorranGestureEvent narration not observed at eastern-descent (0,2)

### Finding 9 (non-blocking, noted for completeness) — Recurring Socket.IO "Not an accepted origin" 400s throughout the session
- **Severity**: Low for this leg specifically (did not block anything observed), but worth flagging since it may explain infra-level combat sync issues
- **Location**: Global, `ws://localhost:3002/socket.io/...`
- **Evidence**: Dozens of `POST /socket.io/?EIO=4&transport=polling...` → 400 `"Not an accepted origin."`, continuously, for the whole session (first seen ~19:56, still recurring at end of run).
- **Confidence**: Reproduced continuously; likely affects all testers on this stack, not phone-specific. Mentioning because Combat beat-progression via the API required an explicit "Wait" move between every attack to force the server to process the beat cycle — GET-polling `/api/combat/status` alone never advanced a move's cooldown — which is consistent with a broken realtime beat-streamer (gated on this same socket connection per `.claude/rules/api-layer.md`). If beat progression is *supposed* to be realtime/socket-driven, this failing handshake could be degrading combat for every player on this stack, phone or desktop.

## Non-bug observations (UX friction / pacing)

- The header title "Heart of Virtue" truncates to "Heart of Virtu…" at 375px width next to the settings gear + Feedback + Account buttons — cosmetic only, header remains functional.
- The room-description panel has a "▼ scroll ▼" affordance that works well and is a good pattern for long room text on a short viewport.
- The MAP tab's combined d-pad-overlaid-on-mini-map is a genuinely good mobile adaptation — it keeps both movement and spatial awareness on one screen without needing two separate tabs for the same information.
- The Inventory category sidebar (vertical icon list) adapts well to portrait phones — much better than a horizontal tab row would have been.
- The SKILLS panel's weapon-type tab row (13 tabs: Axe, Basic, Bludgeon, ...) overflows horizontally with no visible scroll-affordance beyond a partially-cut-off tab at the edge; horizontal scroll does work (confirmed via mouse-wheel deltaX), but there's no chevron/fade hint that more tabs exist off-screen.
- Inventory item detail view's tip text reads "Tip: Left-click on an item to see details." — desktop-centric phrasing ("left-click") on what is otherwise a fully-realized touch UI.
- The item name "Earthen Shortswor…" truncates in the inventory grid card; full name is available in the detail view, so this is cosmetic only.

## Summary of what's playable on a phone

**Works well**: exploration hub (panels, inventory, party, attributes, skills, commands, interact), the map/movement combo screen, NPC LLM chat (choice-driven UI), victory/loot dialogs, settings, account panel, feedback form, world/local map rendering.

**Broken / needs a fix before shipping to phones**: combat is **not playable** via touch (4 of 5 action categories, including the flee option, are dead on tap — Finding 4, Critical); VN-style story-event dialogue is **unreadable** at this width (one-word-per-line text column — Finding 5, Critical). Both are systemic component bugs, not scene-specific, so fixing each component once should resolve every instance across the game.
