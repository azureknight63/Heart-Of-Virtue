## 3. Findings

### Finding #1 — GorranGestureEvent never fires on the Grondia→Eastern Descent transition
- **Severity:** High (event not firing — beta doc's own bug criteria for Scene 4)
- **Location:** eastern-descent (0, 2) "GrondiaEasternGate", reached via Grondia (15,5) "Eastern Gate" passageway
- **Steps to reproduce:**
  1. From Grondia (15,5), INTERACT → "Eastern Gate" → ENTER → "[1] STEP THROUGH"
  2. Arrive at eastern-descent (0,2)
  3. Check `GET /api/world/events/pending` or the UI for any event dialog
- **Expected:** `GorranGestureEvent` fires — Gorran places his palm on the sealed gate, farewell/acknowledgment beat plays (per `src/story/ch03.py` docstring: "fires once on first entry to the tile ... any time the player arrives here from another tile").
- **Actual:** No event fires. `pending()` returns `{"events": [], "success": true}` immediately on arrival, and no dialogue ever appears at this tile.
- **Root cause (confirmed by reading source):** `GorranGestureEvent.check_conditions()` (`src/story/ch03.py:47-56`) bails out early unless `player.previous_tile` is truthy:
  ```python
  prev = getattr(self.player, "previous_tile", None)
  if prev is None:
      return
  ```
  `Player.teleport()` (`src/player/_movement.py:14-59`), which `Passageway._commit_teleport()` (`src/objects.py:846-854`) calls for every passageway crossing including the Eastern Gate, **never sets `player.previous_tile`**. By contrast, `GameService.move_player` (`src/api/services/game_service.py:1216`) explicitly sets `player.previous_tile = tile` before a directional move, with a comment citing issue #377 and naming `GorranGestureEvent` as the consumer. The Eastern Gate is the *only* way from Grondia (15,5) into eastern-descent (0,2) — Grondia's own map JSON gives that tile only a `west` exit — so this is not an alternate/QA-only path being tested instead of the "real" one; it is the sole intended trigger, and it is broken.
- **Evidence:** `pending()` API response `{"events": [], "success": true}` right after arrival; screenshot `T3_002_t3_02_egate_arrival.png` shows the tile with no Gorran dialogue.
- **Confidence:** Reproduced once, but root-caused precisely in source — the code path guarantees this fails every time via the passageway, deterministically. No test in the repo exercises this end-to-end; `tools/harness/scenarios/ch03_events.py:126` manually sets `player.previous_tile` before calling the event directly, side-stepping the real teleport path and masking the bug.

### Finding #2 — Session-start level-up gate can block a fresh session with no explanation of scale
- **Severity:** Medium
- **Location:** Grondia (15,5) "GateEast", immediately on session load
- **Steps to reproduce:** Start a fresh `legb` session.
- **Expected:** Normal level-up flow (a couple of points to allocate, if any).
- **Actual:** A "LEVEL UP" modal appears immediately, blocking ALL other UI (movement, INTERACT, everything) with **71** available attribute points and the message "Must spend all points to continue." The only quick way out is the RANDOMIZE button; manually allocating 71 points one at a time via the dropdown (1 point per submission, per the visible UI) would be extremely tedious.

Likely an artifact of how the `legb` scenario seeds "Scenes 0-3 already played" (stacked level-ups from simulated defeats never got their points spent) rather than a bug a normal player would hit — but if a real player's account ever accumulates a large backlog of unspent points (e.g. after an offline level-up chain), this is a genuine friction/soft-lock risk since the modal cannot be dismissed without fully resolving it.

### Finding #3 — Combat Socket.IO CORS misconfiguration causes a continuous error storm and intermittent UI unresponsiveness during combat
- **Severity:** Medium (environment-specific — see caveat)
- **Location:** All combat encounters on the `legb` stack (port 3002/5002)
- **Steps to reproduce:** Enter any combat on `legb`.
- **Expected:** Socket.IO connects for the real-time combat beat stream (`COMBAT_SOCKET_STREAMING`/`VITE_COMBAT_SOCKET`), or degrades silently if disabled.
- **Actual:** The browser console is flooded, multiple times per second, with:
  ```
  POST http://localhost:3002/socket.io/?EIO=4&transport=polling&... 400 (Bad Request)
  "Not an accepted origin."
  ```
  This runs continuously for the whole combat duration (100+ identical events per fight). While this was happening, combat move-selection panels intermittently failed to respond to Playwright clicks — `<div class="modal-overlay">` transiently intercepted pointer events, and open panels (MANEUVER, target-selection) would silently close themselves before a follow-up click could land, requiring several retries to submit a single move through the UI.
- **Root cause (confirmed by reading source):** `Config.CORS_ORIGINS` in `src/api/config.py:101-106` is a hardcoded list containing only `localhost:3000` and `localhost:3001`. `SOCKETIO_CORS_ALLOWED_ORIGINS` (`config.py:152`) binds to that same list, and `DevelopmentConfig` never overrides it. Port 3002 (the `legb` stack's frontend) is simply not in the allow-list, so `flask-socketio` rejects every handshake from this origin. There is no environment-variable override — it's a hardcoded Python list.
- **Evidence:** dozens of console/network events captured, e.g. `{"status": 400, "text": "\"Not an accepted origin.\""}`.
- **Confidence:** Root cause fully confirmed via source. **Caveat:** this specific failure (two frontends on non-standard ports 3001/3002 talking to two backends) is an artifact of running two parallel QA stacks side by side, not something a real single-frontend deployment would hit. However, (a) the underlying config *is* a hardcoded allow-list rather than derived from the actual configured frontend origin, which is a fragile pattern in general, and (b) the practical effect — degraded combat-UI responsiveness — is real and affected testability. Recommend either making `CORS_ORIGINS` configurable per-stack for QA, or confirming this has no equivalent risk in a production single-origin deployment. Note that Combat itself remained fully completable via the REST fallback (`/api/combat/status`, `/api/combat/move`) throughout, so this is not a soft-lock.

### Finding #4 — Ferry Landing at WaterStep (Nomad Camp map) loops the player back to the tile they entered from, with no crossing acknowledgment
- **Severity:** Medium (behavior surprising, but overlaps the beta doc's declared "known gap")
- **Location:** eastern-descent-nomad-camp (0, 2) "Water Step" → Passageway "Ferry Landing"
- **Steps to reproduce:**
  1. Complete MaraFirstContactEvent at RiversEdge (1,2); she says "head to the ferry landing and we'll be off."
  2. Walk west to WaterStep (0,2).
  3. INTERACT → Ferry Landing → enter → "[1] Step through"
- **Expected:** Some acknowledgment of the arranged crossing (even minimal — Mara narration, a fee deduction, a story flag) — or at minimum, arrival at a genuinely new location west of the river.
- **Actual:** Player is teleported to `eastern-descent` (2,6) "Eastern Bank" — the exact tile complex used to walk INTO the camp in the first place (a round trip back to the east-side descent map, not the west side). No Mara dialogue plays, no fee is referenced, no story flag changes that I could detect from the client side.
- **Evidence:** `where()` before: `nomad-camp (0,2)`; after "step through": `eastern-descent (2,6)` — the same tile reached by walking east out of the camp.
- **Confidence:** Reproduced once. **Caveat:** `docs/development/beta-test-scope-grondia-arc.md`'s "Known Gaps" section explicitly says "No river-crossing completion event... the crossing is narrative only... do not file the absence of a post-crossing story flag as a bug." That covers the *absence* of a flag. It does not obviously cover a full round-trip back to the identical starting tile, which reads more like a placeholder destination (`teleport_tile: [2, 6]` in the map JSON) than "no completion event." Flagging for the story/design team to confirm whether this destination is deliberate scaffolding or should be revisited.

### Finding #10 — Keyboard Enter does not reliably dismiss the final stage of some multi-stage dialogs
- **Severity:** Low (UX/accessibility), medium confidence it's a real issue vs. driver artifact
- **Location:** Observed on the final stage of MaraFirstContactEvent and the first stage of DevetIntroEvent
- **Steps to reproduce:** Reach the last "click to finish" / "Close" stage of a multi-stage story dialog; press Enter repeatedly instead of clicking.
- **Expected:** Enter dismisses the dialog like it does for the middle stages of the same conversation.
- **Actual:** 20-30 consecutive `Enter` presses produced *zero* change in the dialog (identical content every time); a single direct mouse click on the dialog body or its "Close" button dismissed it immediately.
- **Confidence:** Reproduced twice at two different events, but this could be a focus-management quirk specific to how Playwright's `keyboard.press` targets whatever element currently has DOM focus (which may have drifted after a prior click) rather than a genuine keyboard-accessibility bug for real users. Flagging as "possibly a driver artifact — needs verification with a real keyboard user."

## 5. Non-bug observations

- The GorranGestureEvent gap aside, the scripted Nomad Camp scenes (Camp Entry greeting, Mara's two scenes, Devet's intro, Liss's observation) are genuinely well-written and consistently on-voice for each character — this is the strongest content on the route.
- Ambush timing is inconsistent by enemy type: `RockRumbler` triggers an "Enemy Encounter" the instant you step onto its tile; `TalusHound`/`ScarpAdder` wait until your *next* movement attempt on that same tile before ambushing. Not necessarily wrong, but worth designer awareness since it reads as a minor inconsistency.
- At HighLedge, immediately after the Rock Rumbler's defeat, the tile's ambient flavor text ("Rock Rumbler Ehrodutit is shuffling about") remained visible under the Victory/Loot dialog for a few seconds even though the engine's own NPC list had already dropped the Rumbler; it self-corrected as soon as the loot dialog was closed. Purely cosmetic, not filed as a separate bug.
- `where()` occasionally lists Gorran as present at a tile when the ambient tile-flavor text doesn't mention him (e.g. right after arriving at HighLedge) — minor UI/engine text-completeness gap, not blocking.
- The container-discovery flow (hidden object → Search Area → reveal → open → Take All/individual Take) works cleanly and matches the "fair puzzles" design principle (hint text present before discovery).
- Save/Load 403s ("Cloud saves require a registered account") fired constantly in the background on every tile transition — expected/known, not filed per the primer.
