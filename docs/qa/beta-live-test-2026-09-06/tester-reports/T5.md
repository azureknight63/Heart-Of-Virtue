## Findings

### F-01 — Combat never ends in the client: permanent soft-lock after victory
- **Severity:** Critical (blocks play; unrecoverable by reload)
- **Location:** Eastern Descent (1,2) HighLedge and (3,3) ScreeShelf — any combat
- **Steps to reproduce (from session start):**
  1. Log in, spend the level-up points, walk INTERACT → Eastern Gate → (0,2), then east to (1,2).
  2. Fight the Rock Rumbler. Win it.
  3. Observe the Combat screen after the log prints `Victory! Gained exp: …`.
- **Expected:** A victory summary and a loot prompt, then a return to Exploration.
- **Actual:** The screen stays in Combat. The battlefield header resets to a pristine `BEAT 0 / 0 STANDING / Enemies (0) / NO MOVES COMMITTED YET`, the five category buttons remain no-ops, and there is no "continue", "leave", or "return" affordance anywhere. The only trace of the victory is a log line you must scroll to.
  - **First occurrence (1,2):** a page reload *did* surface the `✨ VICTORY!` dialog (EXPERIENCE GAINED / LEVEL UPS & GROWTH / "⚡ 1 item available to collect — next step" / MINIMIZE / COLLECT LOOT →), which then led to a good two-phase loot screen. So the dialog exists; it is simply never mounted at the moment combat ends.
  - **Second occurrence (3,3):** two full reloads produced **no** dialog and left the client in Combat permanently. The run ended here.
- **Evidence (server vs client disagreement, from the page console):**
  ```
  GET /api/combat/status  →  { "combat_active": false, "battle_state": { "status": "active" } }
  POST /api/combat/abort  →  { "success": false, "error": "Not in combat" }
  ```
  …while the client renders `Heart of Virtue - Combat`, `BEAT 12`, `0 STANDING`, `HEAT PRESSING 1.24×`. The server also self-contradicts (`combat_active:false` alongside `battle_state.status:"active"`), which is probably what the client is keying on.
  Combat log at the moment of the lock: `[19:57:53] Rock Rumbler Etiskeax exploded into fragments of light!` / `Victory! Gained exp: Basic: 10, Sword: 12`.
- **Confidence:** reproduced twice; the second is worse than the first.

### F-02 — At the start of a fight the five move-category buttons are silently dead
- **Severity:** Critical (blocks play)
- **Location:** Eastern Descent (1,2), first combat of the session
- **Steps:** Enter combat → click OFFENSIVE, then MANEUVER, MISC, DEFENSIVE, INVENTORY.
- **Expected:** A move panel opens.
- **Actual:** Nothing happens. No panel, no toast, no console error, no network request. The buttons are not disabled — `disabled:false, opacity:1, cursor:pointer` for all five (measured in the page) — so there is no visual signal that the click was ignored. The header shows `BEAT 0`, `Enemies (0)`, `1 STANDING` and stays there indefinitely.
- **Meanwhile the engine was fully ready.** `GET /api/combat/status` at that exact moment:
  ```
  awaiting_input: true,  input_type: "move_selection",  status: "active",  beat: 1,
  available_options: 12 entries  (Attack: fatigue_cost 45, stage_beats {prep 2, execute 1, recoil 2, cooldown 4};
                                  Advance / Withdraw / Turn / Rest / Check / Wait / Use Item / Shoot Bow …)
  enemies: [{ name: "Rock Rumbler Asbo", hp: 48, max_hp: 48 }]
  suggested_moves: [{ move_name: "Advance", score: 80,
                      reasoning: "Close the distance to bring offensive moves into range." }]
  ```
  So the header's `BEAT 0` and `Enemies (0)` were both stale by one beat and one enemy, and the panel had 12 options it refused to render.
- The same buttons worked normally in the *second* fight, where the header showed `BEAT 1` on arrival. The failure correlates with the client being stuck on the pre-first-beat state — very likely a downstream effect of F-03.
- **Confidence:** seen once for the dead state, once for the working state; the API evidence is unambiguous either way.

### F-03 — Socket.IO reconnect storm: every polling POST returns 400, forever
- **Severity:** High (drives F-01/F-02; hammers the server continuously)
- **Location:** Global, all screens
- **Actual:** `read_network_requests` shows an endless cycle — `GET /socket.io/?EIO=4&transport=polling` → 200, then `POST /socket.io/?…&sid=<new sid>` → **400 BAD REQUEST**, then a fresh handshake with a new `sid`. The session id rotates every cycle (`b5obJYwTs…` → `YKTPUDEl6jN2…` → `E9Uo1z5JBrCL…`). 492 requests and 251 console messages logged in one session, of which **78+ are these 400s**. The client falls back to polling `/api/combat/status`.
- This is **not** in the primer's known-noise list. Given COMBAT_SOCKET_STREAMING was verified working on Alpha (2026-08-06), this looks like a regression or a `legb`-stack config problem. It plausibly explains why combat state arrives stale (F-02) and never transitions on completion (F-01).
- **Confidence:** reproduced continuously for the whole session.

### F-04 — HP is unreadable on the exploration and combat screens
- **Severity:** High (player will misunderstand something that matters; pillars 3 and 5)
- **Location:** Global
- **Actual:** Jean's health is shown only as two unlabeled vertical capsules flanking the heart menu. Measured in the DOM: bare `<div>`s, 19 x 190 px, tracks `rgba(255,68,68,0.05)` (left) and `rgba(255,170,0,0.05)` (right), with a fill child. **No text, no number, no `title`, no `aria-label`, no `role="progressbar"`.** There is no tooltip.
- Jean starts this session at **100/252 HP — 40% health** — and nothing on the exploration screen says so. You only learn it by opening ATTRIBUTES.
- In **combat** it is worse: no HP for Jean, Gorran or the enemy anywhere on screen, even though the API carries all of it (`player 100/252`, `Gorran 326/326`, `Rock Rumbler 48/48`, plus per-target `health` objects inside every move's `target_previews`). Pillar 3 says "every number is explainable and the UI can show every roll"; the combat screen shows none of them.
- Pillar 5 says "nothing conveyed by color alone" — this is the clearest violation in the build.
- **Confidence:** reproduced throughout.

### F-05 — The movement d-pad is the one control below the 44 px minimum
- **Severity:** High (pillar 5 is explicit about 44 px)
- **Location:** Exploration, World Map panel
- **Actual:** All eight direction buttons measure **40 x 40 px**. Every other control in the app clears the bar — header buttons 44x44/75x44/72x44, heart-menu buttons 89x56, combat categories 86x54. Only the most-used control in the game misses it.
- Secondary: the d-pad lives *inside* the World Map panel on the opposite side of the screen from the room description it acts on, which is an odd home for the primary verb.
- Disabled states are legible (dim grey border vs bright lime) **and** duplicated in text — `Exits: east, west` under the map. That part is good and should be kept.
- **Confidence:** measured.

### F-06 — Room description is clipped to 200 px with 149 px of empty space directly below it
- **Severity:** High (pillar 4: "exploration is the UI" — the clipped part is the actionable part)
- **Location:** Exploration, all tiles
- **Actual:** The description box is a fixed 200 px tall (measured: `clientHeight 200`, `font-size 16px`, `line-height 24px` — about five lines). At GateEast the visible five lines are pure scene-setting; everything that tells you what to *do* is below the fade:

  Gorran is bumbling about.

- It does scroll, but the persistent `▼ scroll ▼` hint is painted **on top of** the last line rather than below it, so the bottom line is always partly occluded.
- Same pattern recurs in the COMBAT LOG, which shows `▲ scroll ▲` and `▼ scroll ▼` at once over a ~3-line window.

### F-07 — Zero semantic landmarks or headings; focus ring is a near-invisible UA default
- **Severity:** High (accessibility)
- **Location:** Global
- **Actual:** Counted in the page: `header 0, main 0, nav 0, aside 0, footer 0, h1 0, h2 0, h3 0`. A screen-reader user gets an undifferentiated list of buttons with no way to jump to the room description or the map.
- Focus: the entire stylesheet set contains only three `:focus`/`:focus-visible` rules — `.nx-logo-link:focus-visible`, `.landing-page .field input:focus`, `.input-field:focus`. No game control has a focus style. Tabbing to the Account button yields `outline: rgb(90, 60, 0) auto 2px`, i.e. the browser default, rendered dark brown on a near-black header — effectively invisible in the screenshot.
- Several controls have no accessible name at all: the LEVEL UP dialog, the EVENT dialog, the ENEMY ENCOUNTER dialog and the VICTORY dialog all read as bare `dialog` in the a11y tree; the three INTERACT rows read as bare `button`; in the OFFENSIVE panel the **Attack** card is an unnamed `button` while the disabled Shoot Crossbow card is named **"No valid target in range"** — named by its error rather than by the move.
- (CHARACTER STATS does it right: `aria-labelledby=":r3:-title"`. Use that everywhere.)
- **Confidence:** measured.

### F-08 — Battlefield token ring colours contradict the ally/enemy convention
- **Severity:** High (player will target the wrong thing)
- **Location:** Combat, battlefield map
- **Actual:** At combat start J (Jean) and G (Gorran) are lime and R (the Rumbler) is red — the obvious reading. After the first committed move, **G turns red with a red "2" badge and R turns green with a green "5" badge**; later R is orange and G still red. Three combatants, three different ring colours, no legend on screen and no entry in the Overview panel explaining them. The badge digits are unexplained too (beats-to-act, presumably).
- Whatever the rings encode, they collide head-on with the ally/enemy colour language the same screen established thirty seconds earlier.
- **Confidence:** reproduced in both fights.

### F-09 — Tactical Advisor narrates the *previous* battle
- **Severity:** High (misleading)
- **Location:** Combat, (3,3) ScreeShelf
- **Actual:** During the fight with **Rock Rumbler Etiskeax**, the advisor's "ANALYSIS OF PREVIOUS CYCLE" quoted the previous fight verbatim: *"Jean struck Rock Rumbler **Asbo** for 61 damage! Rock Rumbler **Asbo** exploded into fragments of light!"* — Asbo was the (1,2) Rumbler, already dead. A player is told the enemy in front of them has already been destroyed.
- The combat log corroborates the identity mix-up: `[19:57:51] Gorran lashes out at Rock Rumbler **Asbo** with extreme violence!` logged *during the Etiskeax fight*.
- Related: the advisor's recommendation card shows a confident **"85%"** badge next to the text *"Tactical analysis unavailable; Attack is a viable fallback."* A percentage next to a disclaimer of having no analysis is self-contradictory. `NEURAL TACTICAL ENGINE ACTIVE` in the panel footer is developer branding in a player-facing UI.
- **Confidence:** seen once, with two independent corroborating strings.

### F-10 — Event dialogs advertise keyboard shortcuts that do nothing
- **Severity:** High (the hint is wrong, and it is the only stated way to advance)
- **Location:** All story events
- **Steps:** (0,2) GorranGestureEvent. Dialog reads `[1] STEP THROUGH` with the hint **"Press 1-1 to select"**. Press `1` — with the document focused, and again after clicking inside the dialog.
- **Actual:** Nothing. Three attempts over ~8 s each. Clicking the button works.
- Next stage reads **"▸ click or press Enter to continue"**. Pressing `Enter` does nothing; clicking works.
- **This is not a harness artifact:** `Escape` correctly closed the Combat Glossary in the same session and the same pane, so key events do reach the app.
- Cosmetic but embarrassing: **"Press 1-1 to select"** is a `Press {min}-{max}` template with no `n == 1` special case; it appears on every single-choice event.
- **Confidence:** reproduced three times, with a working-keyboard control case.

### F-11 — The event chain uses four different continue verbs and stacks three dismiss affordances at once
- **Severity:** Low
- **Location:** (0,2) GorranGestureEvent, three stages
- **Actual:** In one uninterrupted event you are asked to: `[1] STEP THROUGH` → *"click or press Enter to continue"* → *"click to finish"* → and then a state where **"▸ click to finish" is still displayed** alongside a new **CLOSE** button *and* **"or click anywhere to continue…"** — three competing affordances, one of them already stale.
- Panel close verbs across the app: `CLOSE SHEET`, `DISMISS`, `Close`, `CLOSE BOOK`, `CLOSE`, `✕`. **`DISMISS` on the PARTY dialog is genuinely ambiguous** — it reads as "dismiss Gorran from the party", not "close this window".
- **Confidence:** reproduced.

### F-12 — Event prose is centre-aligned italic monospace in a fixed-height box, with no skip
- **Severity:** Low (pacing/readability)
- **Location:** All event dialogs
- **Actual:** The narrative — the game's primary delivery vehicle — renders as **centred, italic, monospace** at ~65 characters per line. Centred multi-line prose gives a ragged left edge, so the eye has to re-find each line start; italic monospace compounds it.
- The box is a fixed ~240–250 px tall regardless of content: an eight-word line ("A worn path descends east along the bluff's edge.") floats in the vertical centre of a mostly empty box.
- Typewriter speed measured at roughly **40 chars/s** (a 335-character passage took ~8 s), which is a reasonable default. But there is **no way to skip or fast-forward it** and no text-speed setting (see F-13), so a fast reader waits. The continue affordance only appears after the animation completes, so during the run the dialog offers nothing at all.
- **Confidence:** timed once, observed on every event.

### F-13 — Settings has no accessibility options; "Beat timeline" is on but reads as unlabeled chips
- **Severity:** Low
- **Location:** Settings dialog
- **What is good:** MUSIC / SOUND EFFECTS toggles are labelled **"ON"/"OFF" in text** plus colour; sliders show min, max and current value; COMBAT SPEED is a 5-segment 0.5x–2x selector; and both EXPERIMENTAL toggles carry a full plain-English paragraph explaining what they do. That explanatory pattern is the right one and should spread.
- **Missing:** no text-size, no reduced-motion, no high-contrast, and — given F-12 — no typewriter/text-speed control. For a text game whose core loop is reading animated prose, text speed is the obvious omission.
- **"Beat timeline: ON"** promises "a schedule of who resolves next and when, above the battlefield". Before the first committed move nothing appears there at all; after one it renders as two bare name chips (`⚔ Rock Rumbler Asbo`, `⚔ Gorran`) with `+5` / `+7` underneath and no header, no axis and no legend. A player cannot tell that this is the schedule the setting described.
- **Confidence:** seen once each.

### F-14 — First thing the player sees is a 67-point allocation chore in an unnamed dialog
- **Severity:** Low (first-run friction)
- **Location:** Session start, before any gameplay
- **Actual:** The session opens on a blocking **LEVEL UP** modal — `Available Points: 67`, a single attribute dropdown, a number field, ALLOCATE POINTS / RANDOMIZE, and the line *"Must spend all points to continue."* There is no explanation of what any of the seven attributes does, no preview of the derived stats they feed (ATTACK, ACCURACY, EVASION, PROTECTION all exist on the character sheet), and no recommended build. The interaction is dropdown → number → submit, repeated, rather than a row of +/- steppers with a running total.
- The dialog has **no accessible name** (bare `dialog` in the a11y tree).
- **What works:** entering 99 against 67 available produced **"⚠ Not enough points available."** — a warning glyph plus text, correctly not colour-alone.
- **Confidence:** seen once (it is the start state).

### F-15 — Panel-level polish issues
- **Severity:** Low
- **Location:** Various dialogs
  1. **Header title collides with the settings gear.** "Heart of Virtue - Exploration" runs underneath the ⚙️ button (gear occupies x 269–313) instead of truncating. `frontend.md` requires ellipsis truncation here.
  2. **CHARACTER STATS — text collision.** In CORE ATTRIBUTES, "Intelligence" overlaps its value and "BASE: 20" wraps onto two lines on top of the label. Endurance/Charisma have no gap between label and value.
  3. **CHARACTER STATS — buff/debuff by colour alone.** Values are green above base, red below, orange equal (Finesse 24/base 20 green; Charisma 17/base 18 red; Speed 20/base 20 orange). No arrow, no `+`/`−` sign, no key.
  4. **PARTY** calls the stat **VITALITY** where CHARACTER STATS calls it **HP**; the bar is solid red at 326/326 (full health rendered in the danger colour); the "USE ITEM" button is a mid-blue that is not in the token palette (lime / cyan `#00ccff` / orange / red / purple).
  5. **INVENTORY** truncates "Sharp Shortsword…" in a fixed-width card that is the only card in a 500 px-wide, otherwise empty list. Sort chips (Value/Weight/Atk/Rarity) show no active or direction state. The footer "Close" is sentence-case grey where every other button in the app is uppercase lime/orange.
  6. **SKILLS** defaults to the **AXE** tab while Jean has a sword equipped, so the book opens on a weapon class the player does not use. The tab strip overflows and is cut mid-word at the modal edge with only a thin scrollbar and no chevrons. Bright solid `LEARN (50)` buttons out-shout the ability names. `LEARN (n)` never says what n is (XP? gold?).
  7. **COMMANDS** is one of six top-level menu buttons and contains only `MENU` and `SAVE` floating in a large empty box, plus `[DEBUG MODE ACTIVE]` in the footer — the only place the build admits it is in debug mode, buried in the least-visited panel.
  8. **Eastern Gate object** offers two visually identical bright-lime primaries, **ENTER** and **EAST**, with nothing explaining the difference.
  9. **INTERACT** renders NPC/object descriptions in CSS `text-transform: uppercase` prose, truncated at ~30 chars ("A MASSIVE CREATURE THAT SOMEWHA…"), which is both harder to read and destroys the proper nouns.
  10. **Loot screen** titles itself **"VICTORY — PHASE 2 OF 2: LOOT"** (developer language), and its item detail popover rendered **clipped off the left edge of the viewport**, losing roughly 40% of the card.
  11. **ACCOUNT** puts a solid-red **LOG OUT** as the heaviest button, immediately beside an outline **CLOSE**, with no confirmation — destructive-action prominence inverted, on a build where saves are currently failing.
  12. **Feedback validation** fires as a toast in the top-right corner of the screen, ~500 px from the empty TITLE field, which itself gets no error border and no focus. Nothing marks TITLE as required beforehand.
- **Confidence:** each seen once, all in screenshots.

## What works well (do not regress these)

1. **The Combat Glossary.** Searchable, filtered by category (TIME / MOVES / RESOURCES / POSITION / DAMAGE / EFFECTS), and every entry ends with a `▸` line tying the concept back to a specific pixel on screen — *"You will know a beat has passed when the BEAT counter above the battlefield ticks up."* It explains Beat, the four stages, and Cooldown better than most shipped tactics games. Footer: *"Also opens from any underlined term · Esc to close"*, and Esc genuinely works. This is pillar 4 executed properly. Its only problem is that it hides behind an 18 x 18 px `?`.
2. **The OFFENSIVE move panel (when it renders).** Each card carries the move name, `Fatigue: 45`, a four-segment prep/execute/recoil/cooldown bar, the total in beats, and the description. Unavailable moves state **why** — *"⚠ No valid target in range"* — with **"range"** as an underlined link straight into the glossary. That is the single best interaction in the build.
3. **The item detail view.** A labelled Type / Subtype / Damage / Weight / Value / Rarity grid, a `FTH +2` bonus chip, a `✓ Equipped` status with a glyph rather than a colour, `← Back` alongside `✕`, and a red trash-iconed **Drop** clearly separated from the green **Unequip**.
4. **The loot screen's weight maths.** *Current carry weight 10.1 / 72.0 lb · Selected loot adds 0.0 lb · Total after pickup 10.1 lb*, with a bar. Exactly the "every number is explainable" pillar, and it lets you make the decision without arithmetic.
5. **The combat log's prose.** `Jean winds up for a strike…` → `Gorran's attention snaps to Jean. He hasn't stopped fighting, but now he's watching.` → `Jean struck Rock Rumbler Asbo for 61 damage!` → `Rock Rumbler Asbo dropped Gold x 42!`, colour-keyed by actor. It is the only element that reliably explains what just happened. It deserves far more than three visible lines.
6. **Exits stated in text** under the map (`Exits: east, west`) as well as by button state, and the map legend pairing every glyph with a word.
7. **The Feedback form** — tabs, a numbered steps-to-reproduce scaffold, a severity selector, and an anonymity checkbox that explains its consequence.

## Non-bug observations

- The right-hand **World Map** panel gets ~430 px of vertical space for a field of dots with two or three lit cells, and its full-width bright-orange header is the highest-contrast element on the screen. The eye lands on the map title rather than on the room description, which is the actual content. The hierarchy is inverted relative to pillar 4.
- The `EVENT RESULT` modal for the (0,2) event reproduces the tile description almost verbatim; when you close it, the same paragraph is sitting behind it in the room panel. The player reads it twice.
- The five combat category buttons collapse to unlabeled ~40 x 14 px stubs whenever the HEAT meter, Tactical Advisor and combat log are all expanded — the primary verbs get squeezed out by the readouts.
- On viewport resize the layout does not reflow until the next React render; it snapped back into place only after a click.
- `1 STANDING` (and later `0 STANDING`) is ambiguous with three combatants on the field.
- No exploration-side equivalent of the combat glossary exists, and no in-game explanation of what the seven attributes do — the player meets them first in the mandatory 67-point allocation gate.
